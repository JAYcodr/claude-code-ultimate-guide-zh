# 实现前探索

> **可信度**：第 2 层 — 经从业者研究验证（决策质量 +20-30%，识别的替代方案 +40%）。
> **来源**：[MetalBear 工程博客](https://metalbear.com/blog/engineering-ai-use/)、arXiv 从业者研究

编码前让 Claude 提供带权衡的多种方法。这防止锚定偏差——对第一个提出的解决方案执念的倾向。

## TL;DR

```
1. 仅描述问题（无代码，无先入之见）
2. 请求 3-5 种带权衡的方法
3. 请求量化比较
4. 选择方法
5. 然后实现
```

关键洞见：**一旦模型提出具体解决方案，它可能无意中缩小你的思维。**

## 模式

### 步骤 1：仅问题陈述

从问题开始，而不是解决方案方向：

```
我需要在 Node.js API 中处理用户会话。
需求：
- 支持 10K 并发用户
- 会话数据：用户 ID、权限、偏好
- 必须经受服务器重启
```

**不要这样**（锚定 Redis）：
```
我想用 Redis 做会话。我怎么实现它？
```

### 步骤 2：请求多种方法

```
给我 4 种解决这个问题的方法。
每种包括：
- 架构概述
- 优缺点
- 性能特征
- 实现复杂度
```

### 步骤 3：量化比较

```
现在按 1-10 分对以下方面排名：
- 延迟（越低越好）
- 可扩展性（10K → 100K 用户）
- 运维复杂度
- 开发时间
```

### 步骤 4：选择，然后实现

```
我选择方法 B（JWT + Redis 混合）。
现在按照 src/auth/ 中现有模式实现它。
```

## 反锚定提示词

| 提示词类型 | 模板 | 效果 |
|-------------|----------|---------|
| **全新开始** | "忽略任何先前的想法。为 [X] 生成 4 种新颖方法" | 强制多样性 |
| **反思循环** | "生成 3 个选项，然后批评每个，然后推荐" | 自我纠正（-25% 锚定偏差） |
| **量化权衡** | "按 [指标1]、[指标2]、[指标3] 排名，1-10 分" | 客观比较 |
| **魔鬼代言人** | "反对你推荐的最强论点是什么？" | 暴露隐藏权衡 |
| **约束变化** | "现在用 [相反约束] 解决相同问题" | 扩展解决方案空间 |

### 示例：反锚定提示词

```
我需要一个 REST API 的分页，支持 1M+ 条记录。

注意：不要先建议基于偏移的分页。
生成 4 种不同的分页策略，包括至少一种非常规方法。每种：

1. 它是如何工作的（2-3 句）
2. 最佳用例
3. 最差用例
4. 在 1M 条记录时的性能

然后推荐一种，解释为什么它对我的用例优于其他。
```

### 反思循环提示词

```
对于实现实时通知：

阶段 1：生成 3 种方法（WebSockets、SSE、长轮询）
阶段 2：每种，列出生产中可能出错的 2 件事
阶段 3：基于阶段 2，哪种方法最 resilient？

展示每个阶段的推理。
```

## 何时使用

### 使用探索

| 场景 | 为什么 |
|----------|---------|
| 全新功能 | 没有现有模式可遵循 |
| 架构决策 | 影响大，难以逆转 |
| 多种有效方法 | 需要明智选择 |
| 不熟悉的领域 | 不知道不知道什么 |
| 团队分歧 | 获得选项的中立分析 |

### 跳过探索

| 场景 | 为什么 |
|----------|---------|
| Bug 修复 | 解决方案通常从症状明显 |
| 单一有效方法 | 没有真正的选择要做 |
| 时间紧迫的热修复 | 速度 > 完美 |
| 遵循现有模式 | 决策已经做出 |
| 微小变更 | 开销不值得 |

## 与 Claude Code 集成

### 使用计划模式

探索发生在**进入计划模式之前**：

```
# 步骤 1：探索（还不在计划模式中）
我需要给 API 添加缓存。有什么选项？

# Claude 回复 4 种方法

# 步骤 2：选择
我们用方法 C（Cloudflare 边缘缓存）。

# 步骤 3：计划（按 Shift+Tab 两次进入计划模式）
使用 Cloudflare Workers 实现边缘缓存。
遵循我们现有的中间件模式。
```

### 使用 CLAUDE.md

将探索触发器添加到你的项目指令：

```markdown
## 工作流偏好

### 新功能前
实现新功能时，先探索 3-4 种带权衡的方法再承诺实现。
使用量化比较（1-10 分）：
- 性能
- 可维护性
- 实现时间
```

### 使用任务工具

将探索作为任务跟踪：

```
TaskCreate: "探索缓存方法"
TaskCreate: "根据分析选择方法"
TaskCreate: "实现缓存失效"
TaskCreate: "向响应添加缓存头"
# 用 TaskUpdate 标记完成进度
```

## 反模式

### 过早锚定

```
# 错误
"我想用 Redis 做缓存。怎么设置？"

# 正确
"我需要 API 响应缓存。有什么选项？"
```

你在探索之前已经消除了 90% 的解决方案。

### 浅层比较

```
# 错误
"Redis 和 Memcached 哪个更好？"

# 正确
"比较 Redis、Memcached 和进程内缓存：
- 50MB 缓存大小
- 读密集型工作负载（95% 读）
- 单服务器部署
包括延迟、内存开销和运维复杂度。"
```

### 忽略权衡

```
# 错误
"直接告诉我最好的方法"

# 正确
"选择方法 A 而非 B 我会牺牲什么？
什么场景会让我后悔这个选择？"
```

### 分析瘫痪

```
# 错误
为一个简单功能探索 10 个选项

# 正确
设限："给我你排名前 3 的方法，不要更多"
做决定，必要时迭代
```

## 示例会话

### 初始探索

```
用户：我需要在 React 仪表板中实现实时更新。
      仪表板显示约 50 个每 5 秒更新的指标。
      目前我们轮询，但用户抱怨数据陈旧。

Claude：以下是 4 种方法：

**A) WebSockets**
- 全双工，服务器可以随时推送
- 优点：延迟最低，真正的实时
- 缺点：连接管理、扩展复杂性
- 最适合：亚秒级更新、双向通信

**B) Server-Sent Events (SSE)**
- 单向服务器 → 客户端流
- 优点：简单、基于 HTTP、自动重连
- 缺点：仅单向、浏览器连接有限
- 最适合：仪表板馈送、通知

**C) 长轮询**
- 客户端持有请求直到数据就绪
- 优点：到处可用、简单回退
- 缺点：延迟更高、服务器负载更大
- 最适合：遗留兼容性

**D) GraphQL Subscriptions**
- 基于 WebSocket 的 GraphQL schema
- 优点：类型安全、选择性更新
- 缺点：需要 GraphQL 基础设施
- 最适合：现有 GraphQL API

用户：按我们的用例排名（React、50 个指标、5s 刷新，
      团队没有 WebSocket 经验）。

Claude：评分（1-10，越高越好）：

| 方法 | 延迟 | 复杂度 | 团队契合度 | 可扩展性 |
|----------|---------|------------|----------|-------------|
| WebSockets | 10 | 4 | 3 | 7 |
| SSE | 8 | 8 | 8 | 8 |
| Long Polling | 5 | 9 | 9 | 5 |
| GraphQL Subs | 9 | 3 | 2 | 7 |

**推荐：SSE**
简洁性和实时能力最佳平衡。
你的团队一天就能实现，它轻松处理 50 个指标 × 5 秒更新。
以后需要双向或亚秒级更新再升级到 WebSockets。

用户：我们就用 SSE。现在实现它。
```

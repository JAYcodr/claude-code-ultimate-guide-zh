# 使用 Claude Code 进行计划驱动开发

> **可靠性等级**：第 1 层 — 基于 Claude Code 原生 /plan 模式。

对任何复杂任务使用 `/plan` 模式。Claude 探索代码库（只读），然后为你提出实现计划供你批准。

## TL;DR

```
1. 进入计划模式（Shift+Tab 两次）或问复杂问题
2. Claude 探索代码库（只读）
3. Claude 将计划写入 .claude/plans/
4. 你审查并批准
5. Claude 执行
```

## /plan 工作流

### 步骤 1：进入计划模式

用 `Shift+Tab` 切换计划模式（按两次循环 Normal → Auto-Accept → Plan）：
```
# 按 Shift+Tab 两次进入计划模式
#（UI 中出现计划模式指示器）
```

或问一个自动触发计划模式的复杂问题：
```
我应该如何重构认证系统以支持 OAuth？
```

### 步骤 2：Claude 探索

在计划模式中，Claude：
- 读取相关文件
- 搜索模式
- 理解现有架构
- 不能做任何更改

### 步骤 3：Claude 编写计划

Claude 在 `.claude/plans/[name].md` 创建计划文件：

```markdown
# 计划：为 OAuth 重构认证

## 摘要
在保持现有邮箱/密码认证的同时添加 OAuth 支持。

## 要修改的文件
- src/auth/providers/index.ts（添加 OAuth 提供者）
- src/auth/middleware.ts（处理 OAuth 令牌）
- src/config/auth.ts（OAuth 配置）

## 要创建的文件
- src/auth/providers/oauth.ts
- src/auth/providers/google.ts

## 实现步骤
1. 创建 OAuth 提供者接口
2. 实现 Google OAuth 提供者
3. 更新中间件检测令牌类型
4. 添加 OAuth 路由
5. 更新配置 schema

## 风险
- 迁移期间破坏现有会话
- 提供者之间的令牌格式差异
```

### 步骤 4：你审查

审查计划：
- 完整性（所有需求已覆盖）
- 正确性（适合你代码库的方法）
- 范围（没有过度工程）

### 步骤 5：批准并执行

```
看起来不错。按计划执行。
```

或请求更改：
```
修改计划：也添加 GitHub OAuth 支持，不只是 Google。
```

## 何时使用

### 使用计划模式

| 场景 | 为什么 |
|----------|---------|
| 多文件变更 | 预先查看所有受影响文件 |
| 架构变更 | 编码前验证方法 |
| 新功能 | 确保完整实现 |
| 陌生代码库 | 让 Claude 先探索 |
| 风险操作 | 执行前审查 |

### 跳过计划模式

| 场景 | 为什么 |
|----------|---------|
| 单行修复 | 显而易见，低风险 |
| 拼写修正 | 无需计划 |
| 简单问题 | 探索，而非实现 |
| 添加注释 | 微小变更 |

## 计划文件结构

计划以自动生成的名称存储在 `.claude/plans/` 中。

### 典型计划部分

```markdown
# 计划：[标题]

## 摘要
[1-2 句概述]

## 上下文
[为什么需要这个变更]

## 要修改的文件
[将变更的现有文件列表]

## 要创建的文件
[新文件列表]

## 要删除的文件
[要删除的文件列表（如果有）]

## 实现步骤
[有序步骤列表]

## 测试策略
[如何验证变更]

## 风险和缓解措施
[可能出错的事情及如何处理]

## 未解决的问题
[继续前要澄清的事情]
```

## 与其他工作流集成

### 计划 + TDD

```
# 进入计划模式（Shift+Tab 两次），然后：

我需要实现一个速率限制器。
先计划测试用例，再写实现。
```

Claude 以正确的 TDD 顺序计划测试和实现。

### 计划 + 规范优先

```
# 进入计划模式（Shift+Tab 两次），然后：

审查 CLAUDE.md 中的支付处理规范。
创建一个满足所有验收标准的实现计划。
```

### 计划 + 任务工具

批准后，让 Claude 分解为任务：

```
批准。从这个计划创建任务并开始实现。
```

## 技巧

### 明确范围

```
# 太模糊（通过 Shift+Tab 两次进入计划模式后）
改进 API

# 更好
在 /users 端点添加游标导航分页。
保持与现有客户端的向后兼容性。
```

### 请求计划修改

```
计划看起来不错，但：
- 为网络失败添加错误处理
- 暂时跳过缓存优化
- 包含回滚程序
```

### 用于架构决策

```
# 进入计划模式（Shift+Tab 两次），然后：

我正在考虑两种状态管理方法：
A) Redux Toolkit
B) Zustand

探索代码库并推荐哪种更适合。
```

### 保存计划用于文档

`.claude/plans/` 中的计划作为决策文档：
- 为什么选择某些方法
- 预期变更哪些文件
- 实现顺序原理

## 高级：自定义 Markdown 计划（Boris Tane 模式）

> **来源**：Boris Tane，Cloudflare 工程主管 — ["How I use Claude Code"](https://boristane.com/blog/how-i-use-claude-code/)（2026 年 2 月）。9 个月生产使用。
> **可靠性等级**：第 2 层 — 从业者验证模式，非官方 Anthropic 文档。

当计划模式不够用时，在写任何代码之前进行迭代式人/代理计划。

### 为什么自定义计划优于 /plan

| 因素 | 计划模式（原生）| 自定义 .md 计划 |
|--------|----------------|-----------------|
| **持久性** | 上下文压缩时丢失 | 存活，可共享 |
| **审查面** | 基于聊天，线性 | 结构化文件，diff |
| **迭代** | 对话中来回 | 注释文件，重新运行 |
| **共享状态** | 每个会话 | "共享可变状态"在人/代理之间 |
| **最适合** | 标准功能，<30 分钟任务 | 复杂功能，架构决策 |

**决策规则**：已知范围使用计划模式（Shift+Tab 两次）。当期望避免误解或想在任何代码行之前明确批准方法时使用自定义 `.md` 计划。

### 三阶段工作流

```
┌─────────────────────────────────────────────────────────────────┐
│  阶段 1: 研究                                              │
│  → 深入提示 → research.md（写入文件，而非口头）                │
├─────────────────────────────────────────────────────────────────┤
│  阶段 2: 计划（注释循环）                                    │
│  → plan.md 草稿 → 人类注释 → 代理更新 → 重复               │
│  → 退出：计划批准，无开放问题                               │
├─────────────────────────────────────────────────────────────────┤
│  阶段 3: 执行                                              │
│  → 按计划执行，决策已做出                                  │
└─────────────────────────────────────────────────────────────────┘
```

---

### 阶段 1：深入研究

Claude 蜻蜓点水不会有好结果。用深入语言强制深度：

```
深入研究这个代码库中的认证系统。
非常详细地理解会话是如何管理的。
涵盖边缘情况、现有模式和任何非显而易见的依赖。

将你的发现写入 research.md — 不要实现任何东西。
```

**为什么有效**："深入"、"非常详细"、"复杂性"将 Claude 从表面扫描转向深入调查。输出必须写入文件——口头摘要在上下文压缩时消失。

**research.md 应该包括**：
- 现有模式和约定
- 文件路径和关键函数
- 非显而易见的依赖
- 识别的约束和风险

---

### 阶段 2：注释循环

Boris Tane 模式的核心。在准备就绪之前迭代 `plan.md`，**在实现之前**。

```
┌──────────────────────────────────────────────────────────────┐
│                    注释循环                                      │
│                                                              │
│  人类提示 ──→ 代理写 plan.md                                │
│       ↑                    ↓                                    │
│  注释计划    人类审查 plan.md                                │
│  （添加评论，        ↓                                        │
│   问问题，    发现问题？                                      │
│   标记权衡）        ├─ 是 → 注释 → 循环                      │
│                      └─ 否 → 批准 → 阶段 3                   │
│                                                              │
│  典型：批准前 1-6 次迭代                                      │
└──────────────────────────────────────────────────────────────┘
```

**保护提示** — 始终包含以防止过早实现：

```
基于 research.md，写一个实现 [功能] 的计划。

包括：方法、受影响的文件路径、关键决策的代码片段、
权衡的考虑和开放问题。

写入 plan.md。还不要实现任何东西。
```

**plan.md 应该包含**：

```markdown
# 计划：[功能名称]

## 方法
[策略和原理]

## 受影响的文件
- path/to/file.ts — 什么变更及原因
- path/to/other.ts — 什么变更及原因

## 关键实现细节
[非显而易见部分的代码片段 — 不是完整实现]

## 权衡
- 选项 A vs B：选择 A 因为 X
- 考虑但拒绝：Y（原因）

## 开放问题
- [ ] 我们应该处理边缘情况 Z 吗？
- [ ] 这会影响移动客户端吗？
```

**注释示例**：

```markdown
## 方法
使用存储在 httpOnly cookie 中的 JWT 令牌。
<!-- 人类注释：✓ 同意。但也考虑刷新令牌轮换 -->

## 开放问题
- [ ] 我们应该在中间件中处理令牌过期吗？
<!-- 人类注释：是的，集中化 — 不要留给每个路由 -->
```

**退出标准** — 计划就绪当：
- 没有剩余的开放问题
- 权衡已记录并同意
- 文件路径具体（不是"某个 auth 文件"）
- 关键片段显示方法，而不只描述它

> "Markdown 文件作为你和代理之间的共享可变状态。" — Boris Tane

---

### 阶段 3：按计划执行

一旦计划批准，实现就是执行——没有剩余的创意决策。

```
实现 plan.md 中的所有内容。
按顺序处理每个项目。
用 [x] 标记完成的任务。
不要在任务之间停下来等待确认 — 继续直到完成。
```

**执行期间的反馈**：
- 保持简洁：短语或截图，而非段落
- 决策已做出 — 将范围变更重定向回 plan.md
- 如果出现意外情况：暂停，更新 plan.md，继续

**心态转变**：阶段 3 是按计划执行。所有思考都发生在阶段 2。

---

### 补充技术

| 技术 | 什么 | 何时 |
|-----------|------|------|
| **樱桃采摘** | 实现 plan.md 的子集 | 计划太大，增量发布 |
| **范围修剪** | 执行前从计划中移除项目 | 降低风险，专注核心 |
| **基于参考的指导** | 指向现有代码："像 auth.ts 那样做" | 强制一致性 |
| **回滚和重新范围** | `git revert` + 用更窄计划重新开始 | 计划出错，干净重置 |

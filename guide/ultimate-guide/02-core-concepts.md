## 2.1 交互循环

每次 Claude Code 交互都遵循以下模式：

```
┌─────────────────────────────────────────────────────────┐
│                      交互循环                            │
├─────────────────────────────────────────────────────────┤
│                                                         │
│   1. 描述    ──→  你说明需求                              │
│        │                                                │
│        ▼                                                │
│   2. 分析    ──→  Claude 探索代码库                       │
│        │                                                 │
│        ▼                                                 │
│   3. 建议    ──→  Claude 提出变更（diff）                  │
│        │                                                 │
│        ▼                                                 │
│   4. 审查    ──→  你阅读并评估                             │
│        │                                                 │
│        ▼                                                 │
│   5. 决策    ──→  接受 / 拒绝 / 修改                       │
│        │                                                 │
│        ▼                                                 │
│   6. 验证    ──→  运行测试，检查行为                        │
│        │                                                 │
│        ▼                                                 │
│   7. 提交    ──→  保存更改（可选）                         │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

### 关键洞察

循环的设计理念是 **你始终掌握控制权**。Claude 提议，你决策。

## 2.2 上下文管理

🔴 **这是 Claude Code 最重要的概念。**

### 📌 上下文管理速查

**各区间**：
- 🟢 0-50%：自由工作
- 🟡 50-75%：开始精打细算
- 🔴 75-90%：立即 `/compact`
- ⚫ 90%+：必须 `/clear`

**上下文过高时**：
1. `/compact`（保存上下文，释放空间）
2. `/clear`（全新开始，丢失历史）

**预防**：只加载必要文件，定期 compact，频繁提交

---

### 什么是上下文？

上下文是 Claude 对话的"工作记忆"。它包括：
- 对话中的所有消息
- Claude 读取过的文件
- 命令输出
- 工具结果

### 上下文预算

Claude 拥有 **200,000 token** 的上下文窗口。把它想象成内存——满了之后，速度会变慢或失败。

### 读取状态栏

状态栏显示你的上下文用量：

```
Claude Code │ Ctx(u): 45% │ Cost: $0.23 │ Session: 1h 23m
```

| 指标 | 含义 |
|--------|---------|
| `Ctx(u): 45%` | 已使用 45% 的上下文 |
| `Cost: $0.23` | 至今的 API 费用 |
| `Session: 1h 23m` | 已过时间 |

### 自定义状态栏

默认状态栏可以增强，加入更多详细信息，如 git 分支、模型名称和文件变更。

**方案 1：[ccstatusline](https://github.com/sirmalloc/ccstatusline)（推荐）**

在 `~/.claude/settings.json` 中添加：

```json
{
  "statusLine": {
    "type": "command",
    "command": "npx -y ccstatusline@latest",
    "padding": 0
  }
}
```

显示内容：`Model: Sonnet 4.6 | Ctx: 0 | ⎇ main | (+0,-0) | Cost: $0.27 | Session: 0m | Ctx(u): 0.0%`

**方案 2：自定义脚本**

创建自己的脚本：
1. 从 stdin 读取 JSON 数据（模型、上下文、费用、git 信息）
2. 向 stdout 输出一行格式化文本
3. 支持 ANSI 颜色

```json
{
  "statusLine": {
    "type": "command",
    "command": "/path/to/your/statusline-script.sh",
    "padding": 0
  }
}
```

在 Claude Code 中使用 `/statusline` 命令自动生成初始脚本。

**可用 JSON 字段（stdin）**：

| 字段 | 类型 | 说明 |
|-------|------|-------------|
| `model` | string | 当前模型名称 |
| `context` | object | `used`、`total`、`percentage` |
| `cost_usd` | number | 会话费用 |
| `git` | object | 分支、暂存/未暂存计数 |
| `rate_limits` | object | Claude.ai 使用量（v2.1.80+） |

**`rate_limits` 对象**（v2.1.80+）— 直接在状态栏中显示 Claude.ai token 使用量，无需打开仪表板：

```json
{
  "rate_limits": {
    "5h":  { "used_percentage": 42, "resets_at": "2026-03-20T15:30:00Z" },
    "7d":  { "used_percentage": 18, "resets_at": "2026-03-23T00:00:00Z" }
  }
}
```

状态栏脚本示例：

```bash
#!/usr/bin/env bash
input=$(cat)
pct_5h=$(echo "$input" | jq -r '.rate_limits["5h"].used_percentage // "?"')
echo "RL: ${pct_5h}%"
```

### 上下文区间

| 区间 | 用量 | 操作 |
|------|-------|--------|
| 🟢 绿色 | 0-50% | 自由工作 |
| 🟡 黄色 | 50-75% | 开始精打细算 |
| 🔴 红色 | 75-90% | 使用 `/compact` 或 `/clear` |
| ⚫ 临界 | 90%+ | 必须清空，否则可能出错 |

### 上下文恢复策略

当上下文过高时：

**方案 1：Compact（`/compact`）**
- 总结对话
- 保留关键上下文
- 减少约 50% 的用量

> **当 `/compact` 出问题时**：压缩操作发生在模型积累最多上下文时，也就是它最分心的时刻。如果模型无法预测工作的方向（例如 auto-compact 在调试中途触发，而你下一条消息是"现在修复 bar.ts 中的那个警告"），它可能会从总结中丢弃与未来相关的信息。缓解方法：主动压缩并带上下文说明：`/compact focus on the auth refactor, drop the test debugging` 引导总结关注下一步重要内容。（来源：Anthropic 内部指南）

**方案 2：Clear（`/clear`）**
- 全新开始
- 丢失所有上下文
- 在切换话题时使用

> **"一个任务，一次对话"** — 在不同轮次中混入无关话题会降低约 39% 的模型准确率。上下文会积累噪声（"上下文腐化"），即使总 token 用量很低也会扭曲判断。在切换不同任务时主动使用 `/clear`，不要等到上下文栏变红。

**方案 3：从此处总结**（v2.1.32+）
- 使用 `/rewind`（或 `Esc + Esc`）打开检查点列表
- 选择一个检查点，选择"Summarize from here"
- Claude 总结从该点开始之后的所有内容，保持之前的上下文完整
- 释放空间同时保留关键上下文
- 比完整 `/compact` 更精确

**方案 4：精准定位**
- 在查询中保持具体
- 避免"读取整个文件"
- 使用符号引用："读取 `calculateTotal` 函数"

### 上下文分类：保留 vs 清除

当接近红色区域（75%+）时，仅靠 `/compact` 可能不够。你需要主动决定在压缩前保留哪些信息。

**优先级：保留**

| 保留内容 | 原因 |
|------|-----|
| CLAUDE.md 内容 | 核心指令必须持久 |
| 正在编辑的文件 | 当前工作上下文 |
| 当前组件的测试 | 验证上下文 |
| 已做的关键决策 | 架构选择 |
| 正在调试的错误信息 | 问题上下文 |

**优先级：清除**

| 清除内容 | 原因 |
|----------|-----|
| 已读但不再相关的文件 | 一次性查阅 |
| 已解决问题的调试输出 | 历史杂音 |
| 过长的对话历史 | 由 /compact 总结 |
| 已完成任务的文件 | 不再需要 |
| 大型配置文件 | 需要时重新读取即可 |

**压缩前检查清单**：

1. **记录关键决策** 到 CLAUDE.md 或会话笔记中
2. **提交待处理变更** 到 git（创建恢复点）
3. **明确说明当前任务**（"我们正在实现 X"）
4. **运行 `/compact`** 来总结并释放空间

**专业提示**：如果你知道压缩后还需要特定信息，明确告诉 Claude："压缩之前，记住我们决定使用策略 A 来处理认证，因为 X。"Claude 会把这些内容包含在总结中。

### 会话记忆 vs 持久记忆

Claude Code 有三个不同的记忆系统。理解差异对高效长期工作至关重要：

| 方面 | 会话记忆 | 自动记忆（原生） | 持久记忆（Serena） |
|--------|----------------|----------------------|---------------------------|
| **范围** | 仅当前对话 | 跨会话，按项目 | 跨所有会话 |
| **管理方式** | `/compact`、`/clear` | `/memory` 命令（自动） | 通过 Serena MCP 的 `write_memory()` |
| **丢失时机** | 会话结束或 `/clear` | 通过 `/memory` 显式删除 | 从 Serena 显式删除 |
| **需要** | 无需额外配置 | 无需额外配置（v2.1.59+） | [Serena MCP 服务器](#82-可用服务器) |
| **用途** | 即时工作上下文 | 关键决策、上下文片段 | 架构决策、模式 |

**会话记忆**（短期）：
- 当前对话中的所有内容
- Claude 读取过的文件、运行过的命令、做过的决策
- 通过 `/compact`（压缩）和 `/clear`（重置）管理
- 关闭 Claude Code 后消失

**自动记忆** *（原生，v2.1.59+）*：
- 内置于 Claude Code — 无需 MCP 服务器或配置
- Claude 自动将有用的上下文（决策、模式、偏好）保存到 `MEMORY.md` 文件
- 按项目组织：`.claude/memory/MEMORY.md` 或 `~/.claude/projects/<path>/memory/MEMORY.md`
- 通过 `/memory` 管理：查看、编辑或删除已保存的内容
- 自动跨会话持久化

**持久记忆**（长期，Serena MCP）：
- 需要安装 [Serena MCP 服务器](#82-可用服务器)
- 通过 `write_memory("key", "value")` 显式保存
- 跨会话持久化
- 适用于：架构决策、API 模式、编码规范

**模式：会话结束保存**

```
# 结束高效会话前：
"把我们的认证决策保存到记忆：
- 选择 JWT 而非 session，原因：可扩展性
- Token 过期时间：15 分钟访问，7 天刷新
- 刷新 token 存储在 httpOnly cookie 中"

# Claude 调用：write_memory("auth_decisions", "...")

# 下一次会话：
"我们之前关于认证的决定是什么？"
# Claude 调用：read_memory("auth_decisions")
```

**何时使用哪种**：
- **会话记忆**：活跃问题解决、调试、探索
- **自动记忆**：希望在下次会话中 Claude 无需手动操作就能重新发现的决策和上下文（v2.1.59+）
- **持久记忆（Serena）**：跨项目的结构化键值存储，用于架构决策
- **CLAUDE.md**：团队规范、项目结构（随 git 版本管理）

**自动压缩与 PostToolUse 记忆捕获 — 需要注意的冲突**：

当剩余上下文低于固定缓冲阈值（大约上下文窗口的最后 6-7%，或有效限制的大约 13K tokens）时，Claude Code 会自动压缩对话。实际上，这会在上下文使用率达到 90-95% 时触发，具体取决于模型的上下文窗口和保留的输出 token。在全量压缩运行之前，Claude Code 还会应用**微压缩**——一种更轻量的处理，选择性压缩较旧的工具结果（文件读取、bash 输出、搜索结果），以逐步释放空间而无需总结整个对话。如果自动压缩失败（例如由于速率限制），它会连续重试最多 3 次，然后才会放弃本次会话。

如果你使用基于钩子的记忆捕获工具（如 claude-mem），通过 `PostToolUse` 保存会话历史，自动压缩可能会在保存管道有机会捕获之前触发并丢弃对话历史。

两种处理方式：

```json
// 方案 1：在项目 settings.json 中禁用自动压缩
//（你通过 /compact 手动管理压缩）
{
  "autoCompactEnabled": false
}
```

```bash
# 方案 2：保持自动压缩开启，但将工具的保存阈值
# 设置到远低于 80%（例如 60% 上下文用量时触发）
# — 查看你的记忆插件的冷却/阈值配置
```

方案 1 提供完全控制，但需要自律。方案 2 在你忘记手动压缩时更安全。指南建议（在 75% 时主动使用 `/compact`）仍然适用——禁用自动压缩只是意味着你自己控制时机。

### 新鲜上下文模式（Ralph Loop）

#### 问题：上下文腐化

研究表明，LLM 性能会随着上下文积累显著下降：
- **聚焦提示与污染提示之间存在 20-30% 的性能差距**（[Chroma，2025](https://research.trychroma.com/context-rot)）
- 对于较旧的 Claude 模型，退化始于约 16K tokens（Chroma，2025）；Anthropic 报告在 1M 上下文窗口上约 300-400K tokens 时出现明显退化（取决于任务，非固定阈值）
- 失败的尝试、错误追踪和迭代历史会稀释注意力

与其在单个会话内管理上下文，不如**为每个任务启动全新的会话**，同时将状态持久化到外部。

#### 模式

```bash
# 标准"Ralph Loop"（Geoffrey Huntley）
while :; do cat TASK.md PROGRESS.md | claude -p ; done
```

> **命名注**："Ralph Loop"在社区中有两种不同用法。Geoffrey Huntley 的原始模式（如上）是关于上下文轮转——生成新会话以避免上下文腐化。另一种用法由 Addy Osmani 等人在 2026 年推广，将该术语应用于多智能体团队中的*原子任务迭代*：选取任务 → 实现 → 验证 → 提交 → 重置上下文 → 重复。两者共享相同的核心机制（带外部状态的无状态循环），但范围不同。当该术语出现而没有注明出处时，需说明是哪个变体。

**状态通过以下方式持久化**：
- `TASK.md` — 当前任务定义及验收标准
- `PROGRESS.md` — 学到的东西、已完成任务、阻塞项
- Git 提交 — 每次迭代原子化提交

**变体：tasks/lessons.md**

交互式会话的轻量替代方案（无需循环）：每次用户纠正后，Claude 更新 `tasks/lessons.md`，记录避免相同错误的规则。每次新会话开始时审查。

```
tasks/
├── todo.md      # 当前计划（可勾选项）
└── lessons.md   # 从纠正中积累的规则
```

与 PROGRESS.md 的区别：`lessons.md` 捕获*行为规则*（"标记完成前先 diff"、"未经询问不要 mock"），而非任务状态。它会随时间累积——规则集越完善，错误率越低。

| 传统方式 | 新鲜上下文 |
|-------------|---------------|
| 在聊天历史中积累 | 每个任务重置 |
| 用 `/compact` 压缩 | 状态保存在文件 + git 中 |
| 上下文在任务间互相污染 | 每个任务获得完整注意力 |

#### 何时使用

| 情况 | 使用 |
|-----------|-----|
| 上下文 70-90%，保持交互 | `/compact` |
| 上下文 90%+，需要全新开始 | `/clear` 然后继续 |
| 长时间自主运行，基于任务 | 新鲜上下文模式 |
| 夜间/AFK 执行 | 新鲜上下文模式 |

**适合场景**：
- 超过 1 小时的自主会话
- 迁移、大型重构
- 具有明确成功标准的任务（测试通过、构建成功）

**不适合场景**：
- 交互式探索
- 无明确规格的设计
- 反馈循环缓慢/模糊的任务

**变体：按关注点划分会话的管道**

不循环同一个任务，而是为每个质量维度分配一个全新会话：

1. **计划会话** — 架构、范围、验收标准
2. **测试会话** — 先写单元测试、集成测试和 E2E 测试（TDD）
3. **实现会话** — 编码直到所有 lint 和测试通过
4. **审查会话** — 专门的安全审计、性能、代码审查会话
5. **重复** — 根据需要调整范围后迭代

这结合了新鲜上下文（每个阶段干净 200K）与 [OpusPlan](#62-opusplan-混合模式)（Opus 用于审查/策略会话，Sonnet 用于实现）。每个会话产生的进度产物输入下一个会话。

#### 实际实现

**方案 1：手动循环**

```bash
# 简单的新鲜上下文循环
for i in {1..10}; do
    echo "=== Iteration $i ==="
    claude -p "$(cat TASK.md PROGRESS.md)"
    git diff --stat  # 检查进度
    read -p "继续？(y/n) " -n 1 -r
    [[ ! $REPLY =~ ^[Yy]$ ]] && break
done
```

**方案 2：脚本**（参见 `examples/scripts/fresh-context-loop.sh`）

```bash
./fresh-context-loop.sh 10 TASK.md PROGRESS.md
```

**方案 3：外部编排器**

- [AFK CLI](https://github.com/m0nkmaster/afk) — 基于任务源的零配置编排

`/compact` 保持对话流。新鲜上下文最大化每个任务的注意力，代价是连续性。

### 哪些操作消耗上下文？

| 操作 | 上下文消耗 |
|--------|--------------|
| 读取小文件 | 低（约 500 tokens） |
| 读取大文件 | 高（约 5K+ tokens） |
| 运行命令 | 中（约 1K tokens） |
| 多文件搜索 | 高（约 3K+ tokens） |
| 长对话 | 持续累积 |

### 上下文耗尽症状

学会识别上下文即将耗尽时的信号：

**策略 6：对重复上下文使用提示缓存（API）**

如果你直接调用 Anthropic API（例如用于自定义智能体或管道），提示缓存可将重复前缀的成本降低高达 90%。

```python
# 用 cache_control 标记稳定部分
response = client.messages.create(
    model="claude-sonnet-4-6-20250514",
    max_tokens=1024,
    system=[
        {
            "type": "text",
            "text": "<你的大型系统提示/代码库上下文>",
            "cache_control": {"type": "ephemeral"}  # 缓存此前缀
        }
    ],
    messages=[{"role": "user", "content": "修复 auth.ts 中的错误"}]
)
```

**提示缓存经济学**：

| 操作 | 成本倍数 | TTL |
|-----------|-----------------|-----|
| 缓存写入 | 基础价格 × 1.25 | 5 分钟（默认） |
| 缓存写入（延长） | 基础价格 × 2 | 1 小时 |
| 缓存读取（命中） | 基础价格 × 0.1 | — |
| 延迟减少 | 长提示最多减少 85% | — |

**盈亏平衡点**：5 分钟 TTL 内 2 次缓存命中。之后就是纯节省。

**规则**：
- 每次请求最多 **4 个缓存断点**
- 缓存键 = 精确前缀匹配（单个字符变化 = 缓存未命中）
- 将断点放在大型稳定部分之后：系统提示、工具定义、代码库上下文
- 对于 Claude Code 本身：缓存由 CLI 自动处理——这适用于你基于 Claude 构建的 API 级工作流

> 文档：[prompt caching](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching)

#### Claude Code 如何自动处理缓存

Claude Code 无需任何配置即可管理提示缓存。理解其机制有助于你做出保持高缓存命中率和低成本的决策。

**缓存前缀层次结构**

Claude Code 的每个 API 调用都按以下固定顺序组织内容：`tools → system → messages`。缓存匹配始终从前缀的开头开始。稳定的工具列表 + 稳定的 CLAUDE.md + 增长的对话历史意味着前两层几乎总是缓存命中，只有新的消息轮次需要重新计算。

**20 块回溯——长会话陷阱**

缓存匹配使用约 20 个块的有限回溯窗口。在包含大量工具调用和交换的长会话中，早期对话中的块会落在此窗口之外，变成缓存未命中。实际后果：非常长的会话会逐渐在消息层失去缓存效率。解决方法是 `/compact`——它将对话历史压缩成单个摘要块，重置回溯窗口并恢复高命中率。

**各模型的最低 token 阈值**

块必须满足最小大小才能被缓存。小于阈值的块永远不会被缓存，无论它们有多稳定：

| 模型系列 | 最低 tokens |
|---|---|
| Claude Opus 4.7、Opus 4.6、Opus 4.5、Haiku 4.5 | 4,096 |
| Claude Sonnet 4.6 | 2,048 |
| Claude Sonnet 4.5、Sonnet 4、Sonnet 3.7、Opus 4.1、Opus 4 | 1,024 |
| Claude Haiku 3.5、Haiku 3 | 2,048 |

较短的 CLAUDE.md 文件（约 1,000 tokens 以下）在 Sonnet 模型上可能根本不会被缓存。如果成本优化很重要，确保系统提示超过目标模型的阈值。

**工具结果大小与缓存经济学**

工具结果会进入消息历史并停留在那里直到会话结束。每个后续 API 调用都会重新读取该历史——按缓存读取价格（0.1倍），但仍与大小成正比。一个 500 token 的 `git status` 输出，在之后每轮对话中读取成本为 500 × 0.1×。相同输出如果只有 50 tokens（由 RTK 等工具过滤），成本为 50 × 0.1×——少 90%，并且在会话的每一轮中持续累积。紧凑的工具输出不仅处理更快；它们还使整个缓存前缀的维护成本更低。

同样的逻辑适用于缓存写入：更小的历史前缀意味着更便宜的初始写入（1.25× × 更少的 token）。

**监控自定义管道中的缓存性能**

当在 Anthropic API 之上构建智能体或管道时，响应的 `usage` 对象直接暴露缓存指标：

```python
response = client.messages.create(...)

print(response.usage.cache_creation_input_tokens)  # 此请求写入缓存的 tokens
print(response.usage.cache_read_input_tokens)       # 从缓存读取的 tokens（命中）
print(response.usage.input_tokens)                  # 非缓存输入 tokens
```

跨请求计算命中率：`cache_read / (cache_read + cache_creation)`。比率高于 0.8 意味着提示结构运行良好。低比率通常意味着稳定前缀中的内容在请求之间发生变化——检查系统提示中的时间戳、随机 ID 或动态内容。

目前没有专门针对 Claude Code 会话缓存指标的监控工具。`ccusage` 的成本追踪涵盖总体支出，但不区分缓存命中率。对于自定义管道中的缓存可见性，请解析上面的响应字段。

**实用规则**

- 在会话之间保持 CLAUDE.md 稳定——编辑会一次性使系统缓存失效，然后在下一个请求时重新预热
- 在对话变得很长之前运行 `/compact`，而不是等到性能下降后
- 避免在稳定部分中使用动态内容（日期、随机值、每次请求的上下文）
- 更大的 CLAUDE.md = 更昂贵的缓存写入，但每次读取节省的 token 也更多——约 2 次命中后开始盈利

**已知缓存错误（v2.1.69+）**

两个活跃的错误在 v2.1.69+ 上静默破坏缓存。立即应用以下变通方案：

- **--resume/--continue** 导致每次恢复时完全重建缓存（0% 命中率），因为会话 JSONL 在写入前会去除延迟工具记录。变通方案：修复前避免使用 `--resume`。
- **按会话计费头部** 在第一个系统提示块中注入唯一哈希值，导致每次会话启动和子智能体调用时冷未命中。变通方案：在 `~/.claude/settings.json` 中设置 `"CLAUDE_CODE_ATTRIBUTION_HEADER": "false"`。

参见 [已知问题 → 提示缓存错误](core/known-issues.md) 并运行 `/check-cache-bugs` 进行全面审计。

> 文档：[prompt caching](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching)

# 每次会话设定心理预算
- 快速任务（5-10 分钟）：$0.05-$0.10
- 功能开发（1-2 小时）：$0.20-$0.50
- 深度重构（半天）：$1.00-$2.00

# 如果你持续超预算：
1. 更频繁地使用 /compact
2. 查询更具体
3. 考虑简单任务用 Haiku
4. 减少 MCP 服务器
```

#### 成本与价值

**关于成本的视角**：如果 Claude Code 在任务上为你节省了有意义的时间，API 成本与你的小时费率相比通常微不足道。不要为了 token 成本而过度优化，牺牲生产力。

**何时优化**：
- ✅ 预算紧张（学生、爱好者）
- ✅ 高用量（每天 >4 小时）
- ✅ 团队使用（5 名以上开发者）

**何时不优化**：
- ❌ 你的时间比 API 成本更贵
- ❌ 你花在优化上的时间超过了节省
- ❌ 优化损害了生产力（限制太多）

#### 注重成本的工作流

**预算有限的个人开发者：**

```markdown
1. 先使用 Haiku 进行探索/规划
2. 切换到 Sonnet 进行实现
3. 积极使用 /compact（每 50-60% 上下文时）
4. 限制在 1-2 个 MCP 服务器
5. 所有查询保持具体
6. 尽可能批量操作

月成本估算：$5-$15，20-30 小时
```

**专业开发者：**

```markdown
1. 默认使用 Sonnet（最佳平衡）
2. 根据需要 /compact（70%+ 上下文时）
3. 使用完整 MCP 配置（生产力优先）
4. 不要微优化查询
5. 关键架构决策使用 Opus

月成本估算：$20-$50，40-80 小时
```

**团队：**

```markdown
1. 共享 MCP 基础设施（Context7、Serena）
2. 标准化 CLAUDE.md，避免重复解释
3. 智能体库，避免重新构建模式
4. CI/CD 集成实现自动化
5. 在 Anthropic Console 中追踪每位开发者的成本

月成本估算：$50-$200，5-10 名开发者
```

#### 危险信号（成本浪费指标）

| 指标 | 原因 | 修复 |
|-----------|-------|-----|
| 会话持续 >$1 | 未使用 `/compact` | 在 70% 上下文时设置提醒 |
| 每条消息成本 >$0.05 | 上下文膨胀 | 重新开始 `/clear` |
| 爱好项目每天 >$5 | 过度使用或查询效率低 | 检查查询具体性 |
| Haiku 无法完成简单任务 | 用错了模型层级 | 非平凡任务使用 Sonnet |

#### 订阅计划与限制

> **注**：Anthropic 的计划经常变化。始终在 [claude.com/pricing](https://claude.com/pricing) 验证当前定价和限制。

**订阅限制如何工作**

与 API 按 token 付费不同，订阅使用一种故意不透明的混合模型：

| 概念 | 说明 |
|---------|-------------|
| **5 小时滚动窗口** | 主要限制；发送下一条消息后 5 小时重置 |
| **每周汇总上限** | 次要限制；每 7 天重置。两者同时适用 |
| **混合计数** | 宣传为"消息"但实际容量基于 token，随代码复杂性、文件大小和上下文而变化 |
| **模型权重** | **Opus 消耗的配额是 Sonnet 的 8-10 倍** |

**各计划的近似 Token 预算**（2026 年 1 月，社区验证）

| 计划 | 5 小时 Token 预算 | Claude Code 提示/5h | 每周 Sonnet 小时数 | 每周 Opus 小时数 | Claude Code 访问权限 |
|------|---------------------|------------------------|---------------------|-------------------|-------------------|
| **Free** | 0 | 0 | 0 | 0 | ❌ 无 |
| **Pro**（$20/月） | ~44,000 tokens | ~10-40 次提示 | 40-80 小时 | 不适用（仅 Sonnet） | ✅ 有限 |
| **Max 5x**（$100/月） | ~88,000-220,000 tokens | ~50-200 次提示 | 140-280 小时 | 15-35 小时 | ✅ 完整 |
| **Max 20x**（$200/月） | ~220,000+ tokens | ~200-800 次提示 | 240-480 小时 | 24-40 小时 | ✅ 完整 |

> **警告**：这些是社区测量的估算值。Anthropic 不发布确切的 token 限制，且限制曾未公告即降低（尤其是 2025 年 10 月）。8-10 倍的 Opus/Sonnet 比率意味着 Max 20x 用户尽管每月支付 $200，每周仅能使用约 24-40 Opus 小时。"提示/5h"是 token 预算的大致实际转化——实际容量随任务复杂性、上下文大小和子智能体使用情况显著变化。月度上限：所有计划约 50 个活跃的 5 小时窗口。

**为什么"小时数"有误导性**

"Sonnet 4 小时数"指的是活跃处理期间的**经过的挂钟时间**，而非日历小时。这不能直接转换为 token，除非知道：
- 代码复杂性（更大的文件 = 更高的每 token 开销）
- 工具使用（Bash 执行增加约 245 输入 tokens/调用；文本编辑器增加约 700）
- 上下文重新读取和缓存未命中

**各层级推荐策略**

| 如果你有... | 建议方法 |
|----------------|---------------------|
| **Pro 计划** | 仅 Sonnet；批量会话，避免上下文膨胀 |
| **有限的 Opus 配额** | OpusPlan 必不可少：Opus 规划，Sonnet 执行 |
| **Max 5x** | Sonnet 默认，仅架构/复杂调试用 Opus |
| **Max 20x** | 更多 Opus 自由，但仍需监控每周用量（24-40 小时很快用完） |

**Pro 用户模式**（社区验证）：

```
1. Opus → 创建详细计划（高质量思考）
2. Sonnet/Haiku → 执行计划（经济高效的实现）
3. 结果：关键处最优推理，整体成本更低
```

这正是 OpusPlan 模式自动实现的功能（参见第 2.3 节）。

**监控用量**

```bash
/status    # 显示当前会话：成本、上下文百分比、模型
```

Anthropic 不提供应用内的实时用量指标。社区工具如 [`ccusage`](https://github.com/ryoppippi/ccusage) 可帮助追踪跨会话的 token 消耗。

订阅用量历史：查看 [Anthropic Console](https://console.anthropic.com/settings/usage) 或 Claude.ai 设置。

**历史注**：2025 年 10 月，用户报告了显著的未文档化限制降低，恰逢 Sonnet 4.5 发布。之前每周可持续 40-80 Sonnet 小时的 Pro 用户报告仅 6-8 小时后即触发限制。Anthropic 承认了限制但未解释差异。

**高峰时段（2026 年 3 月）**：2026 年 3 月 26 日，Anthropic 调整了高峰需求期间会话限制的消耗方式——5 小时滚动窗口在**工作日 PT 时间 5am–11am**（GMT 1pm–7pm）期间消耗更快。每周总量不变，但分布不同。Anthropic 引用了 GPU 容量限制；约 7% 的用户遇到了以前不会触发的限制。Max 用户报告在高峰时段单个提示即从 21% 升至 100% 使用率。实用变通方案：将计算密集型智能体任务（长子智能体链、大型重构）移至晚间或周末。非高峰时段使用清除更快，将相同预算延伸到更远。

### 上下文污染（泄漏）

**定义**：当一个任务的信息污染另一个任务时。

**模式 1：风格泄漏**
```
任务 1："创建一个蓝色按钮"
Claude：[创建蓝色按钮]

任务 2："创建一个表单"
Claude：[创建表单...所有按钮都是蓝色的！]
        ↑ "蓝色"泄漏到了新任务

解决方案：使用明确边界
"---新任务---
创建一个表单。使用默认设计系统颜色。"
```

**模式 2：指令污染**
```
指令 1："始终使用箭头函数"
指令 2："遵循项目规范"（其中使用函数声明）

Claude：[瘫痪，在两种风格间切换]

解决方案：明确优先级
"如果冲突，项目规范优先于我的个人偏好。"
```

**模式 3：时间混乱**
```
会话早期："auth.ts 包含登录逻辑"
...2 小时工作后...
你将 auth.ts 重命名为 authentication.ts

Claude："我将修改 auth.ts..."
        ↑ 使用过时信息

解决方案：明确更新
"注意：auth.ts 已重命名为 authentication.ts"
```

**上下文卫生检查清单**：
- [ ] 新任务 = 明确的 markdown 边界
- [ ] 结构性变更 = 明确告知 Claude
- [ ] 矛盾指令 = 明确优先级
- [ ] 长会话（>2 小时）= 考虑 `/clear` 或新会话
- [ ] 行为异常 = 用 `/context` 检查

验证 Claude 是否正确加载了你的配置。

**简单方法**：

```

### 会话交接模式

结束会话或切换上下文时，创建**交接文档**以保持连续性。

**目的**：通过记录状态、决策和下一步操作，弥合会话间的差距。

**模板**：

```markdown
# 会话交接 - [日期] [时间]

## 已完成工作
- [完成的关键任务 1]
- [完成的关键任务 2]
- [修改的文件：列表]

## 当前状态
- [正常运行的部分]
- [部分完成的部分]
- [已知问题或阻塞项]

## 已做决策
- [架构选择 1：原因]
- [技术选择：理由]
- [接受的权衡]

## 下一步
1. [接下来的直接任务]
2. [依赖任务]
3. [后续验证]

## 下次会话的上下文
- 分支：[分支名]
- 关键文件：[列出 3-5 个最相关的]
- 依赖项：[外部因素]
```

**何时创建交接文档**：

| 场景 | 原因 |
|----------|-----|
| 工作日结束 | 明天无缝继续 |
| 上下文限制前 | 在 `/clear` 前保持状态 |
| 切换关注领域 | 不同任务需要全新上下文 |
| 预期中断 | 紧急情况或会议打断工作 |
| 复杂调试 | 记录假设和已尝试的测试 |

**存储位置**：`claudedocs/handoffs/handoff-YYYY-MM-DD.md`

**专业提示**：让 Claude 生成交接文档：

```
你："创建一份我们今日工作的会话交接文档"
```

Claude 会分析 git 状态、对话历史，并生成结构化的交接文档。

**交接三元组模式**：对于团队或多会话工作流，一个三命令协议在基本交接之上添加了显式合并语义。三个命令协同工作：

| 命令 | 职责 |
|---------|-----|
| `/handoff:create` | 从当前会话上下文生成结构化文档 |
| `/handoff:resume` | 加载交接文档，确认理解，等待批准后才开始 |
| `/handoff:update` | 使用分节合并规则（见下）更新现有交接文档 |

关键补充是 `update` 中的分节合并规则：

| 节 | 合并规则 |
|---------|------------|
| 任务、范围 | 保留或细化 |
| 文件 | 合并 — 合并原文件与新接触的文件 |
| 发现 | 追加 — 添加新发现，从不删除先前内容 |
| 已完成工作 | **仅追加** — 添加新条目，从不删除历史，包含提交哈希 |
| 状态 | 替换 — 写入当前状态 |
| 下一步 | 替换 — 写入更新后的检查清单 |

仅追加的"已完成工作"部分创建了跨会话的审计追踪。即使早期工作被修改，修订也作为新条目出现，而非覆盖。

可在本仓库的 `examples/commands/handoff/` 中找到可复用的模板。

> 模式灵感来自 [Packmind 的交接命令三元组](https://github.com/packmind/packmind)（Apache 2.0）。参见 [致谢](./core/credits.md)。

## 2.3 计划模式

计划模式是 Claude Code 的"只看不动"模式。

### 进入计划模式

```
/plan
```

或直接问 Claude：

```
你：我们先规划这个功能，再开始实现
```

### 计划模式允许的操作

- ✅ 读取文件
- ✅ 搜索代码库
- ✅ 分析架构
- ✅ 提出方案
- ✅ 写入计划文件

### 计划模式禁止的操作

- ❌ 编辑文件
- ❌ 运行修改状态的命令

### 何时使用计划模式

| 情况 | 使用计划模式？ |
|-----------|----------------|
| 探索不熟悉的代码库 | ✅ 是 |
| 调查错误 | ✅ 是 |
| 规划新功能 | ✅ 是 |

| 快速编辑已知文件 | ❌ 否 |

> **建议频率**：Boris Cherny（Anthropic Claude Code 主管）大约 **80% 的任务从计划模式开始**——让 Claude 在写一行代码之前先规划。计划批准后，首次执行几乎总是正确的。

### 退出计划模式

按 `Shift+Tab` 切换回普通模式（执行模式）。你也可以直接输入消息，Claude 会问："准备好执行这个计划了吗？"

> **注**：`Shift+Tab` 在会话中切换计划模式和普通模式。从普通模式按两次 `Shift+Tab` 进入计划模式，从计划模式按一次返回。

### 自动计划模式

**概念**：在任何有风险的操作前自动触发计划模式。

**配置文件**（`~/.claude/auto-plan-mode.txt`）：
```
Before executing ANY tool (Read, Write, Edit, Bash, Grep, Glob, WebSearch), you MUST:
1. FIRST: Use exit_plan_mode tool to present your plan
2. WAIT: For explicit user approval before proceeding
3. ONLY THEN: Execute the planned actions

Each new user request requires a fresh plan - previous approvals don't carry over.
```

**启动自动计划模式**：

*macOS/Linux:*
```bash
# 直接
claude --append-system-prompt "Before executing ANY tool..."

# 通过文件（推荐）
claude --append-system-prompt "$(cat ~/.claude/auto-plan-mode.txt)"

# 在 .zshrc/.bashrc 中设置别名
alias claude-safe='claude --append-system-prompt "$(cat ~/.claude/auto-plan-mode.txt)"'
```

*Windows (PowerShell):*
```powershell
# 在 %USERPROFILE%\.claude\auto-plan-mode.txt 创建配置文件，内容同上

# 直接
claude --append-system-prompt "Before executing ANY tool..."

# 通过文件（添加到 $PROFILE）
function claude-safe {
    $planPrompt = Get-Content "$env:USERPROFILE\.claude\auto-plan-mode.txt" -Raw
    claude --append-system-prompt $planPrompt $args
}
```

**结果工作流**：
```
用户："给 User 模型添加一个 email 字段"

Claude（自动计划模式生效）：
┌─────────────────────────────────────────────────────────────┐
│ 📋 PROPOSED PLAN                                            │
│                                                             │
│ 1. Read schema.prisma to understand current model           │
│ 2. Add field email: String? @unique                         │
│ 3. Generate Prisma migration                                │
│ 4. Update TypeScript types                                  │
│ 5. Add Zod validation in routers                            │
│                                                             │
│ ⚠️ Impact: 3 files modified, 1 migration created            │
│                                                             │
│ Approve this plan? (y/n)                                    │
└─────────────────────────────────────────────────────────────┘

用户："y"

Claude：[Executes the plan]
```

**结果**：因为计划在执行前经过验证，token 减少 76%，结果更好。

### 模型别名

Claude Code 通过 `/model` 支持六个模型别名（每个始终解析为最新版本）：

| 别名 | 解析为 | 使用场景 |
|-------|-------------|----------|
| `default` | 你计划层级的最新模型 | 标准使用 |
| `sonnet` | Claude Sonnet 4.6 | 快速、经济 |
| `opus` | Claude Opus 4.7 | 深度推理 |
| `haiku` | Claude Haiku 4.5 | 预算型、高容量 |
| `sonnet[1m]` | 带 1M 上下文的 Sonnet | 大型代码库 |
| `opusplan` | Opus（规划）+ Sonnet（执行） | 混合智能 |

模型也可以通过 `claude --model <alias>`、`ANTHROPIC_MODEL` 环境变量或 settings.json 中的 `"model"` 设置。优先级：`/model` > `--model` 标志 > `ANTHROPIC_MODEL` > settings.json。

**知识截止日期**（每个模型知道什么）：

| 模型 | 知识截止日期 |
|-------|-----------------|
| Claude Opus 4.7 | 尚未发布 |
| Claude Sonnet 4.6 | 2025 年 8 月 |
| Claude Opus 4.6 | 2025 年 5 月 |
| Claude Haiku 4.5 | 2025 年 2 月 |

Claude Code 会在每次会话开始时将活跃模型的知识截止日期注入系统提示。你可以直接问 Claude——"你的知识截止日期是什么？"——来确认当前会话适用的日期。

### OpusPlan 模式

**概念**：使用 Opus 进行规划（优越的推理能力），Sonnet 进行实现（经济高效）。

**为什么用 OpusPlan？**
- **成本优化**：Opus tokens 比 Sonnet 更贵
- **两全其美**：Opus 质量的规划 + Sonnet 速度的执行
- **Token 节省**：规划通常比实现短

**激活**：
```
/model opusplan
```

或在 `~/.claude/settings.json` 中：
```json
{
  "model": "opusplan"
}
```

**工作原理**：
1. 在**计划模式**（`/plan` 或 `Shift+Tab` 两次）→ 使用 **Opus**
2. 在**执行模式**（普通执行）→ 使用 **Sonnet**
3. 根据模式自动切换

**推荐工作流**：
```
1. /model opusplan        → 启用 OpusPlan
2. Shift+Tab × 2          → 进入计划模式（Opus）
3. 描述你的任务           → 获得 Opus 质量的规划
4. Shift+Tab              → 退出到执行模式（Sonnet）
5. 执行计划               → Sonnet 高效实现
```

**使用子智能体的替代方案**：

你也可以按智能体控制模型使用：

```yaml
# .claude/agents/planner.md
---
name: planner
model: opus
tools: Read, Grep, Glob
---
# 策略规划智能体
```

```yaml
# .claude/agents/implementer.md
---
name: implementer
model: haiku
tools: Write, Edit, Bash
---
# 快速实现智能体
```

**Pro 用户注**：OpusPlan 对 Opus token 有限的 Pro 订阅者特别有价值。它让你在关键规划中利用 Opus 推理，同时为更多会话保留 token。

**预算变体：SonnetPlan（社区技巧）**

`opusplan` 硬编码为 Opus+Sonnet——没有原生的 `sonnetplan` 别名。但你可以通过环境变量重新映射 `opus` 和 `sonnet` 别名的解析目标，从而有效创建 Sonnet→Haiku 混合：

```bash
# 添加到 ~/.zshrc
sonnetplan() {
    ANTHROPIC_DEFAULT_OPUS_MODEL=claude-sonnet-4-6 \
    ANTHROPIC_DEFAULT_SONNET_MODEL=claude-haiku-4-5-20251001 \
    claude "$@"
}
```

使用 `sonnetplan` 时，`/model opusplan` 路由：
- **计划模式** → Sonnet 4.6（通过重映射的 `opus` 别名）
- **执行模式** → Haiku 4.5（通过重映射的 `sonnet` 别名）

> **警告**：模型的自我报告（"你是什么模型？"）不可靠——模型并不总是知道自己的身份。相信状态栏（计划模式中显示 `Model: Sonnet 4.6`）或通过计费仪表板验证。GitHub issue [#9749](https://github.com/anthropics/claude-code/issues/9749) 追踪原生支持。

**固定 Opus 4.6（社区技巧）**

Opus 4.7 配备了新的 tokenizer，相同输入根据内容类型可能映射到大约 1.0-1.35x 更多 token，且在更高 effort 级别下会产生更多输出 token（更多推理步骤）。对于额外支出不会转化为更好结果的工作流，固定到 Opus 4.6 可削减成本而不改变行为。

**方案 A — 全局 Opus 4.6（最简单）**

```json
// ~/.claude/settings.json
{
  "model": "claude-opus-4-6"
}
```

所有会话使用 Opus 4.6。无混合。如果需要 1M 上下文窗口，添加 `[1M]`：`"claude-opus-4-6[1M]"`。

**方案 B — 保留 OpusPlan，仅固定 Opus 端（推荐）**

```json
// ~/.claude/settings.json
{
  "model": "opusplan",
  "env": {
    "ANTHROPIC_DEFAULT_OPUS_MODEL": "claude-opus-4-6"
  }
}
```

`opusplan` 仍然在计划和执行模式间切换，但计划模式现在路由到 Opus 4.6 而非 4.7。Sonnet 在执行模式中保持不变。

Shell 变体（非持久化，适合测试）：
```bash
ANTHROPIC_DEFAULT_OPUS_MODEL=claude-opus-4-6 claude
```

**方案 C — 按会话切换（无需配置更改）**

```
/model claude-opus-4-6
```

下次会话重置。适合在提交配置更改前试用。

**验证**：检查计划模式中的状态栏。应显示 `Model: Opus 4.6`，而非 `Opus 4.7`。计费仪表板确认实际计费的模型。

> **权衡**：Opus 4.6 失去了 `xhigh` effort 级别（Claude Code 中 Opus 4.7 的默认值）和 `max` effort 级别（在 Opus 4.6 上返回错误）。知识截止日期也更早：2025 年 5 月 vs 4.7 的未发布。如果你依赖 `max` effort 或需要内嵌 2025 年 5 月之后的知识，请使用 4.7。

### 预热引擎

**概念**：在执行前运行多轮规划和深度思考。就像开车前预热发动机。

标准工作流：思考 → 规划 → 执行。
预热引擎：思考 → 规划 → 更深入思考 → 完善计划 → 最深入思考 → 定稿 → 执行。

**何时使用**：
- 关键架构决策（不可逆、高影响）
- 影响 10+ 文件的复杂迁移
- 陌生领域，第一直觉常出错

**模式**：

```markdown
## 第 1 轮：初步分析
用户：/plan
用户：分析当前的认证系统。关键组件是什么，
      依赖项有哪些，迁移到 OAuth2 的潜在风险是什么？
Claude：[初步分析]

## 第 2 轮：深度挑战
用户：现在使用扩展思考。挑战你自己的分析：
      - 你做了哪些假设？
      - 你遗漏了哪些失败模式？
      - 高级安全工程师会指出什么？
Claude：[更深入的分析，带自我修正]

## 第 3 轮：最终计划
用户：基于两轮分析，编写最终的迁移计划。
      包含回滚策略和每个步骤的风险缓解措施。
Claude：[结合两轮的完善计划]

## 执行
用户：/execute
用户：执行第 3 轮的计划。
```

**为什么有效**：每一轮都迫使 Claude 重新审视假设。第 2 轮通常能捕捉到第 1 轮遗漏的 30-40% 的问题。第 3 轮综合为更稳健的计划。

> **📊 实证支撑 — Anthropic AI Fluency Index（2026 年 2 月）**
>
> 一项分析 9,830 次 Claude 对话的 Anthropic 研究量化了计划审查为什么有效：迭代并**质疑 AI 推理的用户比接受首次输出的用户多 5.6 倍的可能性发现遗漏的上下文和错误**。第二轮审查使发现遗漏内容可能性提高 4 倍。
>
> 预热引擎模式将这一发现操作化：每轮深度挑战触发质疑行为，从而产生可衡量的更好计划。
>
> *来源：Swanson 等人，"The AI Fluency Index"，Anthropic（2026-02-23）— [anthropic.com/research/AI-fluency-index](https://www.anthropic.com/research/AI-fluency-index)*

### Ultraplan

**状态**：研究预览 — 需要 Claude Code v2.1.91+ 和 Claude Code on the web 账户。

**概念**：将规划卸载到 Anthropic 云端，同时你的终端保持空闲。Claude 使用多个 Opus 4.7+ 智能体并行起草计划；你在浏览器中查看，带内联评论，然后选择在云端执行还是将计划传回终端。

这解决了本地计划模式的核心痛点：在复杂任务上，终端在规划运行期间被阻塞数分钟。Ultraplan 异步运行——你可以继续工作，准备好后再回来看。

**工作原理**

1. CLI 启动云会话 → 终端显示实时状态指示器
2. 多个 Opus 4.7+ 智能体并行探索代码库（最长 30 分钟的计划窗口）
3. 浏览器打开计划，带大纲侧边栏、内联评论和 emoji 反应
4. 你反复修改计划——对特定部分评论、请求修订
5. 选择执行位置：云端（创建 PR）或终端（将计划传回）

**激活（3 种方法）**

```bash
# 1. 专用命令
/ultraplan 将认证服务从 session 迁移到 JWT

# 2. 提示中任何位置的触发词
用 ultraplan 规划支付模块的完整重构

# 3. 从本地计划批准对话框
# → 选择"不，用 Claude Code on the web 上的 Ultraplan 完善"
```

命令和关键字路径会先显示确认对话框。本地计划路径跳过该对话框。

**终端状态指示器**

| 状态 | 含义 |
|--------|---------|
| `◇ ultraplan` | Claude 正在研究和起草 |
| `◇ ultraplan needs your input` | 需要澄清 — 打开浏览器链接 |
| `◆ ultraplan ready` | 计划已准备好审查 |

运行 `/tasks` 查看会话链接、智能体活动和**停止 ultraplan** 操作。

**浏览器审查界面**

- **大纲侧边栏**：在章节间导航，无需滚动
- **内联评论**：高亮任何段落，留下有针对性的反馈
- **Emoji 反应**：在不写评论的情况下对某个部分表示赞同或担忧
- **修订循环**：要求 Claude 处理你的评论；它呈现更新后的草稿——按需迭代任意次数

**执行：两种选择**

计划看起来没问题后，在浏览器中选择：

| 选项 | 发生什么 |
|--------|-------------|
| **批准并开始编码** | 云会话实现计划、创建 PR；终端清除 |
| **批准并传回终端** | 计划发送到你的终端，带 3 个子选项 |

传回子选项：
- **在此实现** — 将计划注入当前对话，立即继续
- **开始新会话** — 以计划为上下文的新鲜会话（打印 `claude --resume` 以返回当前会话）
- **取消** — 将计划保存到文件，打印路径

**要求和限制**

| 要求 | 详情 |
|-------------|--------|
| Claude Code 版本 | v2.1.91+ |
| 账户 | Pro、Max、Team 或 Enterprise（非免费层级） |
| 仓库 | 仅 GitHub（无 GitLab、Bitbucket） |
| 提供商 | 仅 Anthropic API — 不可在 Bedrock、Vertex、Foundry 上使用 |
| 冲突 | 与远程控制不兼容（两者都使用 claude.ai/code） |

**Ultraplan vs OpusPlan vs 计划模式**

| 功能 | 计划模式 | OpusPlan | Ultraplan |
|---------|-----------|----------|-----------|
| 执行位置 | 本地 | 本地 | 云端 |
| 终端被阻塞？ | 是 | 是 | 否 |
| 模型 | 当前活跃模型 | Opus（规划）+ Sonnet（执行） | Opus 4.7（多智能体） |
| 审查界面 | 终端滚动条 | 终端滚动条 | 带内联评论的浏览器 |
| 需要 GitHub？ | 否 | 否 | 是 |
| Token 记账 | 计入本地配额 | 计入本地配额 | 云端规划不计入本地配额 |

**何时使用 Ultraplan**

最适合：
- 涉及多个文件的复杂架构变更（服务迁移、大型重构）
- 希望规划运行时继续工作的任务
- 利益相关者需要在实现前审查计划的情况

跳过：
- 简单、聚焦的变更，本地计划模式不到一分钟
- 无互联网或不在 GitHub 上的环境
- 使用远程控制的会话

**Token 注**：早期测试显示云端规划比等效本地计划消耗约 37% 更少的 token（约 55 分钟迁移任务中 82K vs 131K）。云端规划 token 不计入你的本地配额；只有实现 token 计入。

> **另见**：[§9.16 会话传送](#916-会话传送) 了解更广泛的网页 ↔ 终端工作流。Ultraplan 使用相同的云端基础设施，具有规划特定的审查能力。

### Ultrareview（v2.1.114+）

基于云端的并行多智能体代码审查。Ultraplan 处理规划，Ultrareview 处理审查：多个 Opus 4.7 智能体同时读取你的变更，找出细心审查者会发现的错误和设计问题。

### 机制堆叠

**概念**：在关键决策上叠加多个 Claude Code 机制，以获得最大智能。

```
Layer 1: 计划模式         → 安全探索，无副作用
Layer 2: 扩展思考         → 使用思考 token 进行深度推理
Layer 3: 预热引擎         → 多轮细化
Layer 4: 分角色智能体     → 多视角分析
Layer 5: 排列组合         → 系统性变体测试
```

**不是每个任务都需要所有层。** 将堆叠深度与决策影响匹配：

| 决策影响 | 堆叠深度 | 示例 |
|-----------------|-------------|---------|
| 低（修拼写错误） | 0 层 | 直接做 |
| 中（添加功能） | 1-2 层 | 计划模式 + 扩展思考 |
| 高（架构方案） | 3-4 层 | 预热引擎 + 分角色 |
| 关键（迁移） | 4-5 层 | 完整堆叠 |

**反模式**：在琐碎决策上堆叠。如果变更是可逆的且低风险，直接执行。过度规划与规划不足同样浪费。

## 2.4 回退

回退是 Claude Code 的撤销机制。

### 使用回退

通过 `Esc + Esc`（双击 Escape）或 `/rewind` 命令访问。这会打开一个可滚动的检查点列表。

### 回退的功能

回退从检查点列表提供四个不同的操作：

| 操作 | 效果 |
|--------|--------|
| **恢复代码和对话** | 将文件变更和对话都恢复到选定点 |
| **恢复对话** | 保持当前代码，仅回退对话 |
| **恢复代码** | 恢复文件变更，保持对话 |
| **从此处总结** | 从选定点向前压缩对话（释放空间而不回退） |

关键区别：**恢复** = 撤销（恢复状态）。**总结** = 压缩（释放空间而不回退）。检查点在会话间持久化（30 天清理）。

### 限制

- 仅适用于 Claude 的变更（不含手动编辑）
- 仅在当前会话内有效
- Git 提交不会自动回退

### 最佳实践：风险前创建检查点

在有风险的操作前：

```
你：在尝试这种实验性方法之前，先提交当前的内容
```

这会创建一个 git 检查点，你随时可以回退到那里。

### 恢复阶梯：三个撤销级别

出问题时，你有多种恢复选项。使用能解决问题的最轻量级方法：

```
┌─────────────────────────────────────────────────────────┐
│                    恢复阶梯                              │
├─────────────────────────────────────────────────────────┤
│                                                         │
│   第 3 级：Git 恢复（核选项）                            │
│   ─────────────────────────────                          │
│   • git checkout -- <file>    （放弃未提交的变更）        │
│   • git stash                 （暂时保存）               │
│   • git reset --hard HEAD~1   （撤销上次提交）           │
│   • 适用于：手动编辑、多次会话                           │
│                                                         │
│   第 2 级：/rewind（会话撤销）                           │
│   ──────────────────────────                            │
│   • 恢复 Claude 最近的文件变更                           │
│   • 仅当前会话内有效                                    │
│   • 不触及 git 提交                                     │
│   • 适用于：糟糕的代码生成、错误的方向                    │
│                                                         │
│   第 1 级：拒绝变更（内联）                              │
│   ────────────────────────                              │
│   • 审查 diff 时按 'n'                                  │
│   • 变更从未应用                                        │
│   • 适用于：在问题发生前捕捉                             │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

**何时使用每个级别**：

| 场景 | 恢复级别 | 命令 |
|----------|----------------|---------|
| Claude 提出了糟糕的代码 | 第 1 级 | 按 `n` |
| Claude 做了变更，想撤销 | 第 2 级 | `/rewind` |
| 变更已提交，需要完整回滚 | 第 3 级 | `git reset` |
| 实验分支出错 | 第 3 级 | `git checkout main` |
| 上下文损坏，行为异常 | 重新开始 | `/clear` + 重新说明目标 |

**专业提示**：`/rewind` 命令显示一个变更列表供撤销。你可以选择性地回退特定文件而非全部变更。

### 检查点模式：安全实验

对于系统性实验，使用检查点模式创建安全的恢复点：

```
┌─────────────────────────────────────────────────────────┐
│                    检查点工作流                          │
├─────────────────────────────────────────────────────────┤
│                                                         │
│   1. 创建检查点                                         │
│   ────────                                              │
│   git stash push -u -m "checkpoint-before-refactor"     │
│   （保存所有变更，包括未追踪的文件）                     │
│                                                         │
│   2. 自由实验                                           │
│   ────────                                              │
│   尝试有风险的重构、架构变更等                           │
│   如果成功 → 正常提交                                   │
│   如果失败 → 恢复检查点                                 │
│                                                         │
│   3. 恢复检查点                                         │
│   ────────                                              │
│   git stash list              # 找到你的检查点          │
│   git stash apply stash@{0}   # 恢复，不删除             │
│   # 或                                                   │
│   git stash pop stash@{0}     # 恢复并删除               │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

**自动检查点**：创建 Stop 钩子在会话结束时自动创建检查点：

```bash
# .claude/hooks/auto-checkpoint.sh
# 参见：examples/hooks/bash/auto-checkpoint.sh

# 在会话结束时自动创建 git stash
# 命名：claude-checkpoint-{branch}-{timestamp}
# 日志到：~/.claude/logs/checkpoints.log
```

**常见工作流**：

| 场景 | 工作流 |
|----------|----------|
| 有风险的重构 | 检查点 → 尝试 → 提交或恢复 |
| A/B 测试方案 | 检查点 → 尝试 A → 恢复 → 尝试 B → 比较 |
| 增量迁移 | 检查点 → 逐块迁移 → 测试 → 重复 |
| 原型探索 | 检查点 → 实验 → 干净地丢弃 |

**对比分支的优势**：
- 比创建功能分支更快
- 保留未提交的变更
- 快速实验的轻量级方式
- 跨多个文件生效

> **预算调整**（Teams Standard/Pro）：每阶段降一级——表格说 Opus 的地方用 Sonnet，说 Sonnet 的地方在机械实现任务上用 Haiku。社区模式：$25/月 Teams Standard 计划上使用 *Sonnet 规划 → Haiku 实现*。

### Effort 级别

`effort` 参数（Opus 4.6 API）控制模型的**整体计算预算**——不仅仅指思考 token，还包括工具调用、详细程度和分析深度。低 effort = 更少的工具调用，无开场白。高 effort = 更多解释、更详细的分析。

**校准梯度——每级别一个真实提示：**

- **`low`** — 机械性，无需设计决策
  > `"将 src/ 中所有的 getUserById 重命名为 findUserById"` — 查找替换范围，无需推理。

- **`medium`** — 模式清晰，范围明确，单一关注点
  > `"将 api/users.ts 中的 fetchUser() 从回调转换为 async/await"` — 模式已知，范围限定。

- **`high`** — 设计决策、边界情况、多个关注点
  > `"重新设计支付模块中的错误处理：添加重试逻辑、部分故障恢复和幂等性保证"` — 架构选择，而不仅仅是模式应用。

- **`xhigh`** *（Opus 4.7+，v2.1.114+）* — 介于 `high` 和 `max` 之间的额外高级 effort；Claude Code 中 Opus 4.7 的默认值（所有计划）
  > `"调试分布式作业队列中的竞态条件，涉及并发写入和部分读取"` — 比 `high` 更深，比 `max` 更快。

- **`max`** *（仅 Opus 4.7+ — 在其他模型上返回错误）* — 跨系统推理，不可逆决策
  > `"分析 order-service、inventory-service 和 notification-service 之间微服务事件管道的竞态条件"` — 多服务假设测试、对抗性思考。

### 按技能分配 Effort（v2.1.80+）

技能可以在 frontmatter 中声明自己的 effort 级别。技能的值在技能执行期间覆盖会话设置，然后恢复。这样就不需要在机械任务和分析任务之间手动切换 effort。

```yaml
# 机械技能 — 始终快速，绝不浪费推理预算
---
name: release
description: 升级版本、更新 CHANGELOG、提交、推送
effort: low
---

# 分析技能 — 始终深入，不受会话设置影响
---
name: architecture-review
description: 带权衡评估的完整架构分析
effort: high
---
```

**常见技能类型的决策表：**

| 技能类型 | 推荐 effort | 原因 |
|------------|--------------------|-----------|
| 提交、推送、同步 | `low` | 顺序步骤，无需设计决策 |
| Changelog、发布说明 | `low` | 读取 git + 格式化，机械操作 |
| 脚手架、样板代码 | `low` | 模板实例化 |
| 代码审查（单 PR） | `medium` | 模式识别，范围限定 |
| Issue 分类、积压 | `medium` | 分类 + 一些分析 |
| 安全审计 | `high` | 威胁建模，对抗性思考 |
| 架构审查 | `high` | 设计决策，跨组件推理 |
| 多智能体编排 | `high` | 协调 + 规划 |

> **成本模型**：`low` effort 意味着更少的工具调用、无开场白、直接输出。`high` effort 意味着更多的工具调用带解释、详细摘要、更深入的探索。将 effort 匹配到分析能增值的地方——而非以为 "effort = 质量" 一成不变。

## 2.6 心智模型

理解 Claude Code 的"思考"方式让你更高效。

### Claude 眼中的项目

```
┌─────────────────────────────────────────────────────────┐
│                    你的项目                               │
├─────────────────────────────────────────────────────────┤
│                                                         │
│   ┌─────────────┐    ┌─────────────┐    ┌───────────┐   │
│   │   文件       │    │   Git       │    │   配置     │   │
│   │   (.ts,.py)  │    │   历史      │    │   文件     │   │
│   └─────────────┘    └─────────────┘    └───────────┘   │
│          │                  │                  │        │
│          ▼                  ▼                  ▼        │
│   ┌─────────────────────────────────────────────────┐   │
│   │              Claude 的理解                       │   │
│   │   - 文件结构与关系                               │   │
│   │   - 代码模式与约定                               │   │
│   │   - 最近变更（来自 git）                         │   │
│   │   - 项目规则（来自 CLAUDE.md）                   │   │
│   └─────────────────────────────────────────────────┘   │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### Claude 知道的

1. **文件结构**：Claude 可以导航和搜索你的文件
2. **代码内容**：Claude 可以读取和理解代码
3. **Git 状态**：Claude 看到分支、提交、变更
4. **项目规则**：Claude 读取 CLAUDE.md 了解约定

### Claude 不知道的

1. **运行时状态**：Claude 看不到正在运行的进程
2. **外部服务**：Claude 不能直接访问你的数据库
3. **你的意图**：Claude 需要清晰的指令
4. **隐藏文件**：Claude 默认尊重 .gitignore

> **⚠️ 模式放大**：Claude 会镜像它发现的模式。在结构良好的代码库中，它生成一致、惯用的代码。在混乱、没有清晰抽象的代码库中，它会延续混乱。如果你的代码缺少好的模式，在 CLAUDE.md 中显式提供它们，或使用语义锚点（第 2.9 节）。

### 你是主线程

把自己想象成一个 CPU 调度器。Claude Code 实例是工作线程。你不写代码——你**编排**工作。

```
┌─────────────────────────────────────────┐
│           你（主线程）                    │
│  ┌────────────────────────────────────┐ │
│  │  职责：                            │ │
│  │  • 定义任务和优先级                │ │
│  │  • 分配上下文预算                  │ │
│  │  • 审查输出                        │ │
│  │  • 做出架构决策                    │ │
│  │  • 处理异常/升级                   │ │
│  └────────────────────────────────────┘ │
│         │          │          │         │
│    ┌────▼───┐ ┌────▼───┐ ┌────▼───┐    │
│    │工作者1 │ │工作者2 │ │工作者3 │    │
│    │(Claude)│ │(Claude)│ │(Claude)│    │
│    │功能    │ │测试    │ │审查    │    │
│    └────────┘ └────────┘ └────────┘    │
└─────────────────────────────────────────┘
```

**含义**：
- **不要自己写代码**，只要 Claude 能写。你的时间用来做决策，而不是敲键盘。
- **不要微观管理**。给出清晰的指令，然后审查结果。
- **有意识地切换上下文**。像调度器一样，批量处理类似的任务。
- **升级给自己**。当 Claude 卡住时，你介入——然后交还控制。

这种心智模型可以扩展：一名开发者可以在独立任务上编排 2-5 个 Claude 实例（参见 [§9.17 扩展模式](#917-扩展模式多实例工作流)）。

### 从聊天机器人到上下文系统

最常见的错误是把 Claude Code 当成聊天机器人——临时输入请求，期望好的输出。区分随性使用和生产工作流的是思维转变：

> **聊天机器人模式**：你写好的提示。**上下文系统**：你构建结构化上下文，让每个提示都更好。

> *"别再把它当聊天机器人了。给它结构化上下文。CLAUDE.md、钩子、技能、项目记忆。一切都会改变。"*
> — [Robin Lorenz](https://www.linkedin.com/in/robin-lorenz-54055412a/)，AI 工程师（[评论](https://www.linkedin.com/feed/update/urn:li:activity:7426936437746352128?commentUrn=urn%3Ali%3Acomment%3A%28activity%3A7426936437746352128%2C7426941635306987520%29)）

Claude Code 有四层持久上下文，随时间的推移叠加：

| 层 | 作用 | 章节 | 何时设置 |
|-------|-------------|---------|----------------|
| **CLAUDE.md** | 持久规则、约定、项目知识 | [§3.1](#31-记忆文件-claudemd) | 第 1 周 |
| **技能** | 用于一致工作流的可复用知识模块 | [§5](#5-技能) | 第 2 周 |
| **钩子** | 自动护栏（lint、安全、格式化） | [§7](#7-钩子) | 第 2-3 周 |
| **项目记忆** | 跨会话决策和架构上下文 | [§3.1](#31-记忆文件-claudemd) | 持续 |

这些不是独立的功能。它们是同一个系统的不同层次：

- **CLAUDE.md** 教会 Claude *什么*是你的项目需要的（约定、技术栈、模式）
- **技能** 教会 Claude *如何*执行特定工作流（审查、部署、测试）
- **钩子** 自动执行*护栏*（阻止机密泄露、自动格式化、运行 lint）
- **记忆** 跨会话持久化*决策*（架构选择、解决过的权衡）

**之前**（聊天机器人模式）：
> "用 pnpm，别用 npm。还有，记得我们的命名规范是……"
> *（每次会话。每次都这样。复制粘贴上下文。）*

**之后**（上下文系统）：
> CLAUDE.md 自动加载约定。技能确保一致的工作流。
> 钩子零手动努力执行质量。记忆将决策向前传递。

这个转变不在于更好的提示。而在于构建一个系统，让 Claude 每次开始会话时已经知道你需要什么。

> **另见**：[§9.10 持续改进心态](#910-持续改进心态) 关于如何随时间演进这套系统。准备选择合适的机制？[§2.7 配置决策指南](#27-配置决策指南) 用决策树映射所有七个机制。

### 有效沟通

**好的提示**：
```
src/auth/login.ts 中的 login 函数没有正确验证邮箱地址。
加号（+）应该被允许，但现在被拒绝了。
```

**糟糕的提示**：
```
登录不起作用
```

你提供的上下文越多，Claude 越能提供好的帮助。

## 2.8 使用 XML 标签的结构化提示

XML 结构化的提示为复杂请求提供**语义组织**，帮助 Claude 区分任务的不同方面，从而获得更清晰的理解和更好的结果。

### 什么是 XML 结构化提示？

XML 标签作为**带标签的容器**，显式区分指令类型、上下文、示例、约束和预期输出格式。

**基本语法**：

```xml
<instruction>
  你的主要任务描述
</instruction>

<context>
  背景信息、项目细节或相关状态
</context>

<code_example>
  要遵循的参考代码或示例
</code_example>

<constraints>
  - 限制 1
  - 限制 2
  - 需求 3
</constraints>

<output>
  回复的预期格式或结构
</output>
```

### 为什么使用 XML 标签？

| 优势 | 说明 |
|---------|-------------|
| **关注点分离** | 任务的不同方面被清晰划分 |
| **减少歧义** | Claude 知道哪些信息用于什么目的 |
| **更好的上下文处理** | 帮助 Claude 优先处理主要指令而非背景信息 |
| **一致的格式** | 更容易模板化复杂请求 |
| **多面请求** | 具有多个需求的复杂任务保持有序 |

### 常见标签及其用途

**核心指令标签**：

```xml
<instruction>主要任务</instruction>           <!-- 主要指令 -->
<task>特定子任务</task>                       <!-- 单个行动项 -->
<question>关于 X 我该怎么做？</question>       <!-- 明确询问 -->
<goal>达到状态 Y</goal>                       <!-- 期望结果 -->
```

**上下文和信息标签**：

```xml
<context>项目使用 Next.js 14</context>                <!-- 背景信息 -->
<problem>用户报告页面加载缓慢</problem>               <!-- 问题描述 -->
<background>从 Pages Router 迁移</background>         <!-- 历史上下文 -->
<state>当前在 feature-branch</state>                  <!-- 当前状态 -->
```

**代码和示例标签**：

```xml
<code_example>
  // 要遵循的现有模式
  const user = await getUser(id);
</code_example>

<current_code>
  // 需要修改的代码
</current_code>

<expected_output>
  // 结果应该长什么样
</expected_output>
```

**约束和规则标签**：

```xml
<constraints>
  - 必须保持向后兼容
  - 不能对公共 API 做破坏性变更
  - 最大 100ms 响应时间
</constraints>

<requirements>
  - TypeScript 严格模式
  - 100% 测试覆盖率
  - 可访问（WCAG 2.1 AA）
</requirements>

<avoid>
  - 不要对类型使用 any
  - 不要修改数据库 schema
</avoid>
```

### 实用示例

**示例 1：带上下文的代码审查**

```xml
<instruction>
审查此认证中间件的安全漏洞
</instruction>

<context>
此中间件用于处理敏感用户数据的金融应用程序。
我们遵循 OWASP Top 10 指南，需要 PCI DSS 合规。
</context>

<code_example>
async function authenticate(req, res, next) {
  const token = req.headers.authorization?.split(' ')[1];
  if (!token) return res.status(401).json({ error: 'No token' });

  const decoded = jwt.verify(token, process.env.JWT_SECRET);
  req.user = decoded;
  next();
}
</code_example>

<constraints>
- 指出任何安全风险
- 建议 PCI DSS 合规的替代方案
- 考虑时序攻击和 token 泄露
</constraints>

<output>
提供：
1. 发现的安全问题列表
2. 每个问题的严重等级（严重/高/中/低）
3. 带有示例的具体代码修复
4. 额外的安全加固建议
</output>
```

**示例 2：带示例的功能实现**

```xml
<instruction>
为我们的 API 端点添加速率限制系统
</instruction>

<context>
当前技术栈：Express.js + Redis
目前没有速率限制
正在经历特定 IP 的 API 滥用
</context>

<requirements>
- 已认证用户每个 IP 每分钟 100 次请求
- 未认证用户每个 IP 每分钟 20 次请求
- 高级用户的自定义限制（存储在数据库中）
- 返回 429 状态码和 Retry-After 头部
</requirements>

<code_example>
// 我们使用的现有中间件模式
app.use(authenticate);
app.use(authorize(['admin', 'user']));
</code_example>

<constraints>
- 不得影响现有 API 性能
- Redis 连接应该复用
- 优雅处理 Redis 连接失败
</constraints>

<output>
提供：
1. 速率限制中间件实现
2. Redis 配置
3. 单元测试
4. 团队文档
</output>
```

**示例 3：带状态的错误调查**

```xml
<task>
调查为什么用户会话会提前过期
</task>

<problem>
用户报告在活动 5-10 分钟后被登出，
但会话超时配置为 24 小时。
</problem>

<context>
- Next.js 14 App Router 配合 next-auth
- PostgreSQL 会话存储
- 跨 3 台服务器的负载均衡
- 问题始于上周部署 v2.3.0 后
</context>

<state>
v2.2.0（正常）和 v2.3.0（出问题）之间的 Git diff 显示变更了：
- middleware.ts（会话刷新逻辑）
- auth.config.ts（会话策略）
- database.ts（连接池）
</state>

<constraints>
- 不要建议回滚部署
- 生产问题，需要快速解决
- 必须保持会话安全
</constraints>

<output>
提供：
1. 根本原因假设
2. 需要调查的文件（按优先级排序）
3. 要运行的调试命令
4. 带有权衡的潜在修复方案
</output>
```

### 高级模式

**嵌套标签实现复杂层次结构**：

```xml
<task>
重构认证系统
  <subtask priority="high">
    更新用户模型
    <constraints>
      - 保留现有用户 ID
      - 添加邮箱验证迁移
    </constraints>
  </subtask>

  <subtask priority="medium">
    实现 OAuth 提供商
    <requirements>
      - Google 和 GitHub OAuth
      - 复用现有会话逻辑
    </requirements>
  </subtask>
</task>
```

**带标签的多个示例**：

```xml
<code_example label="当前实现">
  // 带回调地狱的旧方式
  getUser(id, (user) => {
    getOrders(user.id, (orders) => {
      res.json({ user, orders });
    });
  });
</code_example>

<code_example label="期望模式">
  // 新的 async/await 模式
  const user = await getUser(id);
  const orders = await getOrders(user.id);
  res.json({ user, orders });
</code_example>
```

**条件指令**：

```xml
<instruction>
优化数据库查询性能
</instruction>

<context>
查询目前对 10,000 条记录需要 2.5 秒
</context>

<constraints>
  <if condition="PostgreSQL">
    - 使用 EXPLAIN ANALYZE
    - 考虑物化视图
  </if>

  <if condition="MySQL">
    - 使用 EXPLAIN 进行查询计划分析
    - 考虑查询缓存
  </if>
</constraints>
```

### 何时使用 XML 结构化提示

| 场景 | 推荐？ | 原因 |
|----------|--------------|-----|
| 简单的一行请求 | ❌ 否 | 开销大于收益 |
| 多步骤功能实现 | ✅ 是 | 分离目标、约束、示例 |
| 带上下文的错误调查 | ✅ 是 | 区分症状与运行环境 |
| 带特定标准的代码审查 | ✅ 是 | 清晰分离代码、上下文、需求 |
| 架构规划 | ✅ 是 | 组织目标、约束、权衡 |
| 快速拼写修复 | ❌ 否 | 不必要的复杂性 |

### 最佳实践

**要做的**：
- ✅ 使用描述性的标签名称以明确目的
- ✅ 在类似请求中保持标签一致
- ✅ 结合 CLAUDE.md 实现项目特定的标签约定
- ✅ 在表示层次结构时逻辑地嵌套标签
- ✅ 使用标签分离"做什么"、"为什么"和"怎么做"

**不要做的**：
- ❌ 对简单请求过度结构化（增加噪音）
- ❌ 混合标签用途（例如代码示例里的约束）
- ❌ 使用没有明确含义的通用标签（`<tag>`、`<content>`）
- ❌ 嵌套过深（超过 3 层难以阅读）

### 限制与考虑

**Token 开销**：XML 标签消耗 token。对于简单请求，自然语言更高效。

**非必需**：Claude 完全能理解自然语言。当结构确实有帮助时再使用 XML。

**一致性很重要**：如果你使用 XML 标签，保持一致性。在会话中混用风格会让上下文困惑。

**学习曲线**：团队成员需要理解标签系统。在 CLAUDE.md 中记录你的约定。

> - 请求有 3 个以上不同方面（指令 + 上下文 + 约束）
> - 歧义导致 Claude 误解你的意图
> - 创建可复用的提示模板
> - 与需要结构化沟通模式的初级开发者合作

### 2.8.1 提示即挑战

Claude Code 团队内部把提示当作**对同行的挑战**，而非对助手的指令。这种微妙的转变能产生更高质量的输出，因为它迫使 Claude 证明自己的推理，而非简单服从。

**团队使用的三种挑战模式**：

**1. 守门人** — 迫使 Claude 在交付前捍卫自己的工作：

```
"Grill me on these changes and don't make a PR until I pass your test"
```

Claude 审查你的 diff，提出关于边界情况的尖锐问题，只有在满意后才继续。这能捕捉被动审查不会发现的问题。

**2. 证据要求** — 要求证据，而非断言：

```
"Prove to me this works — show me the diff in behavior between main and this branch"
```

Claude 运行两个分支，比较输出，呈现具体证据。

**3. 重置** — 在平庸的第一次尝试后，调用全上下文重写：

```
"Knowing everything you know now, scrap this and implement the elegant solution"
```

这迫使带着积累的上下文进行实质性的第二次尝试，而非在薄弱基础上增量修补。

**为什么有效**：挑战比礼貌请求激活更深的推理路径。当 Claude 必须*说服*而非*服从*时，它会激活更彻底的分析并捕捉自己的捷径。

> **来源**：[10 Tips from Inside the Claude Code Team](https://paddo.dev/blog/claude-code-team-tips/)（Boris Cherny thread，2026 年 2 月）

## 2.9 语义锚点

LLM 是统计模式匹配器，训练在大量文本语料上。使用**精确的技术词汇**有助于 Claude 激活训练数据中正确的模式，从而产生更高质量的输出。

### 为什么精确很重要

当你说"干净的代码"时，Claude 可能从几十种解释中任选一个。但当你说"遵循 Clean Architecture 分层、带依赖注入的 SOLID 原则"时，你就将 Claude 锚定到训练中一个特定的、有充分文档的模式。

**关键洞察**：技术术语就像 Claude 知识的 GPS 坐标。越精确，导航越好。

### Claude Code 的常见锚点

| 模糊术语 | 语义锚点 | 为什么有帮助 |
|------------|-----------------|--------------|
| "错误处理" | "带 Either/Result monad 的 Railway Oriented Programming" | 激活函数式错误模式 |
| "干净代码" | "SOLID 原则，尤其是 SRP 和 DIP" | 锁定特定设计原则 |
| "好的测试" | "TDD London School，outside-in 方法" | 指定测试方法论 |
| "好的架构" | "六边形架构（端口与适配器）" | 命名具体模式 |
| "可读代码" | "Screaming Architecture，意图揭示的命名" | 触发特定命名约定 |
| "可扩展设计" | "CQRS + Event Sourcing" | 激活分布式模式 |
| "文档" | "arc42 模板结构" | 指定文档框架 |
| "需求" | "EARS 语法（Easy Approach to Requirements）" | 定位需求格式 |
| "API 设计" | "REST Level 3 with HATEOAS" | 指定成熟度级别 |
| "安全" | "OWASP Top 10 缓解措施" | 激活安全知识 |

### 如何在 CLAUDE.md 中使用

在项目指令中添加语义锚点：

```markdown
# 架构原则

遵循以下模式：
- **架构**：六边形架构（端口与适配器），清晰的领域边界
- **错误处理**：Railway Oriented Programming — 绝不抛出，返回 Result<T, E>
- **测试**：TDD London School — mock 协作者，测试行为而非实现
- **文档**：重要选择使用 ADR（架构决策记录）
```

### 与 XML 标签结合

语义锚点与 XML 结构化提示（第 2.8 节）配合强大：

```xml
<instruction>
  按照 Domain-Driven Design（Evans）重构用户服务
</instruction>

<constraints>
  - 应用六边形架构（端口与适配器）
  - 持久化使用 Repository 模式
  - 错误处理实现 Railway Oriented Programming
  - 遵循 CQRS 做读写分离
</constraints>

<quality_criteria>
  - Screaming Architecture：包结构揭示意图
  - 每个类单一职责原则
  - 依赖反转：依赖抽象
</quality_criteria>
```

## 2.10 数据流与隐私

> **重要**：你与 Claude Code 分享的所有内容都会发送到 Anthropic 服务器。理解这一数据流对保护敏感信息至关重要。

### 发送到 Anthropic 的内容

使用 Claude Code 时，以下数据会离开你的机器：

| 数据类型 | 示例 | 风险等级 |
|-----------|---------|------------|
| 你的提示 | "修复登录错误" | 低 |
| Claude 读取的文件 | `.env`、`src/app.ts` | **高**（如果包含密钥） |
| MCP 查询结果 | 包含用户数据的 SQL 查询结果 | **高**（如果是生产数据） |
| 命令输出 | `env | grep API` 输出 | 中 |
| 错误消息 | 带文件路径的堆栈追踪 | 低 |

### 保留策略

| 配置 | 保留期 | 如何启用 |
|---------------|-----------|---------------|
| **默认** | 5 年 | （默认状态 — 训练已启用） |
| **退出** | 30 天 | [claude.ai/settings](https://claude.ai/settings/data-privacy-controls) |
| **Enterprise（ZDR）** | 0 天 | Enterprise 合同 |

**立即操作**：[禁用训练数据使用](https://claude.ai/settings/data-privacy-controls) 以将保留期从 5 年减少到 30 天。

### 保护敏感数据

**1. 在 `.claude/settings.json` 中阻止访问敏感文件**：

```json
{
  "permissions": {
    "deny": [
      "Read(./.env*)",
      "Edit(./.env*)",
      "Write(./.env*)",
      "Bash(cat .env*)",
      "Bash(head .env*)",
      "Read(./secrets/**)",
      "Read(./**/*.pem)",
      "Read(./**/*.key)",
      "Read(./**/credentials*)"
    ]
  }
}
```

> **警告**：`permissions.deny` 有已知限制。详见 [安全加固指南](./security/security-hardening.md#known-limitations-of-permissionsdeny)。

**2. 绝不将生产数据库连接到 MCP 服务器**。使用带匿名数据的开发/预发布环境。

**3. 使用安全钩子阻止读取敏感文件**（见 [第 7.4 节](#74-钩子自动化工作流)）。

> **完整指南**：完整的隐私文档，包括已知风险、社区事件和企业考虑，见 [数据隐私与保留指南](./security/data-privacy.md)。

## 2.11 底层原理

> **阅读时间**：5 分钟
> **目标**：理解驱动 Claude Code 的核心架构

本节提供 Claude Code 内部机制的概述。完整的深入技术分析，包括图表和来源引用，见 [架构与内部指南](./core/architecture.md)。

### 主循环

Claude Code 的核心是一个简单的 `while` 循环：

```
┌─────────────────────────────────────────────────────────────┐
│                    主循环（简化版）                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   你的提示                                                   │
│       │                                                     │
│       ▼                                                     │
│   ┌────────────────────────────────────────────────────┐    │
│   │   Claude 推理（无分类器、无路由器）                  │    │
│   └───────────────────────┬────────────────────────────┘    │
│                           │                                 │
│              需要工具？    │                                 │
│                     ┌─────┴─────┐                           │
│                    是           否                           │
│                     │           │                           │
│                     ▼           ▼                           │
│              执行工具       文本回复（完成）                  │
│                     │                                       │
│                     └──────── 将结果反馈给 Claude           │
│                                        │                    │
│                               （循环继续）                   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**来源**：[Anthropic Engineering Blog](https://www.anthropic.com/engineering/claude-code-best-practices)

这里没有：
- 意图分类器或任务路由器
- RAG/向量嵌入管道
- DAG 编排器
- 规划器/执行器分离

模型自己决定何时调用工具、调用哪些工具以及何时完成。

### 工具库

Claude Code 有 8 个核心工具：

| 工具 | 用途 |
|------|---------|
| `Bash` | 执行 shell 命令（通用适配器） |
| `Read` | 读取文件内容（最多 2000 行） |
| `Edit` | 修改现有文件（基于 diff） |
| `Write` | 创建/覆盖文件 |
| `Grep` | 搜索文件内容（基于 ripgrep） |
| `Glob` | 按模式查找文件 |
| `Task` | 生成子智能体（隔离上下文） |
| `TodoWrite` | 追踪进度（旧版，见下） |

**工具如何执行**：Claude Code 可以在模型仍在生成回复时就开始执行标记为并发安全的工具（只读操作如 `Read`、`Grep`、`Glob`），从而减少总的回复时间。非并发工具（写操作、bash 命令）等待回复完成后串行执行。当单个回复中出现多个只读工具时，它们会并行运行——默认最多 10 个并发。

### 任务管理系统

**版本**：Claude Code v2.1.16+ 引入了新的任务管理系统

Claude Code 提供两种任务管理方式：

| 功能 | TodoWrite（旧版） | Tasks API（v2.1.16+） |
|---------|-------------------|---------------------|
| **持久性** | 仅会话记忆 | 磁盘存储（`~/.claude/tasks/`） |
| **多会话** | ❌ 会话结束时丢失 | ✅ 跨会话持久化 |
| **依赖关系** | ❌ 手动排序 | ✅ 任务阻塞（A 阻塞 B） |
| **协调** | 单智能体 | ✅ 多智能体广播 |
| **状态追踪** | pending/in_progress/completed | pending/in_progress/completed/failed |
| **说明可见性** | ✅ 始终可见 | ⚠️ TaskGet 才有（不在 TaskList 中） |
| **元数据可见性** | 不适用 | ❌ 输出中永不可见 |
| **多次调用开销** | 无 | ⚠️ N 个完整任务需要 1 + N 次调用 |
| **启用方式** | 始终可用 | 自 v2.1.19 起默认 |

#### Tasks API（v2.1.16+）

**可用工具：**
- `TaskCreate` - 使用层次结构和依赖关系初始化新任务
- `TaskUpdate` - 修改任务状态、元数据和依赖关系
- `TaskGet` - 检索单个任务详情
- `TaskList` - 列出当前任务列表中的所有任务
- ~~`TaskOutput`~~ — **已弃用（v2.1.83+）**。直接使用 `Read` 读取 `.claude/tasks/<id>/output.log`。

**核心功能：**
- **持久存储**：任务保存到 `~/.claude/tasks/<task-list-id>/`
- **多会话协调**：跨多个 Claude 会话共享状态
- **依赖追踪**：任务可以阻塞其他任务（任务 A 阻塞任务 B）
- **状态生命周期**：pending → in_progress → completed/failed
- **元数据**：附加自定义数据（优先级、估算、相关文件等）

**配置：**

```bash
# 启用多会话任务持久化
export CLAUDE_CODE_TASK_LIST_ID="project-name"
claude

# 示例：项目特定任务列表
export CLAUDE_CODE_TASK_LIST_ID="api-v2-auth-refactor"
claude
```

**⚠️ 重要**：使用仓库特定的任务列表 ID 以避免跨项目污染。使用相同 ID 的任务会跨所有使用该 ID 的会话共享。

**任务 schema 示例：**

```json
{
  "id": "task-auth-login",
  "title": "实现登录端点",
  "description": "POST /auth/login 带 JWT token 生成",
  "status": "in_progress",
  "dependencies": [],
  "metadata": {
    "priority": "high",
    "estimated_duration": "2h",
    "related_files": ["src/auth/login.ts", "src/middleware/auth.ts"]
  }
}
```

**何时使用 Tasks API：**
- 跨多个编码会话的项目
- 带依赖关系的复杂任务层次
- 多智能体协调场景
- 上下文压缩后需要恢复工作

**⚠️ Tasks API 限制（关键）**

**字段可见性约束**：

| 工具 | 可见字段 | 隐藏字段 |
|------|----------------|---------------|
| `TaskList` | `id`、`subject`、`status`、`owner`、`blockedBy` | `description`、`activeForm`、`metadata` |
| `TaskGet` | 所有字段 | - |

**影响**：
- **多次调用开销**：审查 10 个任务说明 = 1 次 TaskList + 10 次 TaskGet 调用（11x 开销）
- **无法扫描元数据**：无法按自定义字段（优先级、估算、标签）过滤/排序，除非逐个获取所有任务
- **会话恢复困难**：无法一眼扫过所有任务笔记来决定从哪里恢复

**成本示例**：
```bash
# 低效（如果需要说明）
TaskList  # 返回 10 个任务（无说明）
TaskGet(task-1), TaskGet(task-2), ..., TaskGet(task-10)  # 10 次额外调用

# 总计：审查 10 个任务需要 11 次 API 调用
```

**变通方案**：

1. **混合方法**（推荐）：
   - Tasks API 用于**状态追踪**和**依赖协调**
   - 在仓库中维护 markdown 文件用于**详细实现计划**
   - 示例：`docs/plans/auth-refactor.md` + Tasks 用于状态

2. **主题即摘要模式**：
   - 将关键信息存储在 `subject` 字段（在 TaskList 中始终可见）
   - `description` 用于深度上下文（通过 TaskGet 按需获取）
   - 示例主题：`"[P0] 修复登录错误 (src/auth.ts:45)"` vs `"修复错误"`

3. **选择性获取**：
   - 使用 TaskList 识别需要关注的任务（status、blockedBy）
   - 只对你正在积极处理的任务调用 TaskGet

**来源**：社区实践者反馈（[Gang Rui，2026 年 1 月](https://www.linkedin.com/posts/limgangrui_i-explored-the-new-claude-codes-task-system-activity-7420651412881268736-Hpd6)）

#### TodoWrite（旧版）

**工具**：`TodoWrite` - 创建存储在会话记忆中的任务列表

**功能：**
- 单次会话内的简单任务追踪
- 状态追踪：pending/in_progress/completed
- 会话结束或上下文压缩时丢失

**何时使用 TodoWrite：**
- 单会话、直接的实现
- 快速修复或探索性编码
- Claude Code < v2.1.16
- 简单性优于持久性

**迁移标志**（v2.1.19+）：

```bash
# 临时回退到 TodoWrite 系统
CLAUDE_CODE_ENABLE_TASKS=false claude

# 使用新的 Tasks API（默认）
claude
```

#### 最佳实践

**任务层次设计：**
```
项目（父级）
└── 功能 A（子级）
    ├── 组件 A1（叶子任务）
    │   ├── 实现
    │   └── 测试（依赖实现）
    └── 组件 A2
```

**依赖管理：**
- 创建任务时始终定义依赖关系
- 使用任务 ID（而非标题）进行依赖引用
- 执行前用 `TaskGet` 验证依赖

**状态转换：**
- 开始工作时标记 `in_progress`（防止并行执行）
- 频繁更新以保持可见性
- 仅在完全完成时才标记 `completed`（测试通过、已验证）
- 使用带错误元数据的 `failed` 状态进行调试

**元数据约定：**
```json
{
  "priority": "high|medium|low",
  "estimated_duration": "2h",
  "related_files": ["path/to/file.ts"],
  "related_issue": "https://github.com/org/repo/issues/123",
  "type": "feature|bugfix|refactor|test"
}
```

#### 任务列表作为诊断工具

**诊断原则**：当 Claude 的任务列表与你的意图不匹配时，问题不在于 Claude——在于你的指令。

任务列表充当**指令清晰度的镜子**。如果你让 Claude 规划一个功能，但生成的任务让你吃惊，这种偏差就是诊断信息：

```
你的指令："重构认证系统"

Claude 的任务列表：
- [ ] 读取所有认证相关文件
- [ ] 识别代码重复
- [ ] 提取共享工具函数
- [ ] 更新导入
- [ ] 运行测试

你的反应："这不是我想要的——我想从 session 切换到 JWT"

诊断：你的指令有歧义。"重构" ≠ "替换"。
```

**偏差模式及含义：**

| 偏差类型 | 含义 | 修复 |
|-----------------|---------------|-----|
| 任务过于宽泛 | 指令缺乏具体性 | 添加 WHAT、WHERE、HOW、VERIFY |
| 任务过于狭窄 | 指令太详细，缺少大局 | 说明目标，而不仅仅是步骤 |
| 优先级错误 | 缺少关于什么重要的上下文 | 添加约束和优先级 |
| 缺少任务 | 隐式知识未共享 | 在提示中明确假设 |
| 多余任务 | Claude 推断出你未曾意图的需求 | 添加明确的范围边界 |

**将任务偏差用作工作流：**

```markdown
## 第 1 步：用宽松的指令播种
用户："改进结账流程"

## 第 2 步：审查 Claude 的任务列表（暂不执行）
Claude 生成：[任务列表]

## 第 3 步：与你的心智模型对比
- 缺少：支付重试逻辑？→ 添加到指令
- 意外：UI 重新设计？→ 明确范围（仅后端）
- 顺序错误：测试放在最后？→ 指定 TDD 方法

## 第 4 步：细化并重新规划
用户："实际上，我需要的是：[带具体内容的细化指令]"
```

**专业提示**：在初始规划后运行 `TaskList` 作为**健全性检查**，然后再执行。如果超过 30% 的任务让你意外，你的提示需要改进。迭代提示，而非任务。

### 上下文管理

Claude Code 在 **200K token 上下文窗口**内运行（通过 API 提供 1M 测试版——见 [200K vs 1M 对比](#200k-vs-1m-上下文性能成本与使用场景)）：

| 组件 | 大致大小 |
|-----------|------------------|
| 系统提示 | 5-15K tokens |
| CLAUDE.md 文件 | 1-10K tokens |
| 对话历史 | 视情况 |
| 工具结果 | 视情况 |
| 为回复保留 | 40-45K tokens |

当上下文填满时（VS Code 中约 75%，CLI 中约 95%），较早的内容会被自动总结。然而，**研究表明这会降低质量**（复杂任务性能下降 50-70%）。在逻辑断点处主动使用 `/compact`，或在 85% 时触发**会话交接**，以在压缩历史中保持意图。见 [会话交接](#会话交接模式) 和 [自动压缩研究](core/architecture.md#auto-compaction)。

### 子智能体隔离

`Task` 工具生成带以下特性的子智能体：
- 自己的全新上下文窗口
- 能使用相同工具（Task 本身除外）
- **最大深度为 1**（不能生成孙智能体）
- 只有摘要文本返回主上下文

这防止了探索性任务期间的上下文污染。

### TeammateTool（实验性）

**状态**：部分功能标记，逐步推出中。

TeammateTool 实现**多智能体编排**，智能体之间可以持久通信。与标准子智能体隔离工作不同，队友可以通过结构化消息进行协调。

**核心功能**：

| 操作 | 目的 |
|-----------|---------|
| `spawnTeam` | 创建命名智能体团队 |
| `discoverTeams` | 列出可用团队 |
| `requestJoin` | 智能体请求加入团队 |
| `approveJoin` | 团队负责人批准加入请求 |
| 消息传递 | 基于 JSON 的智能体间通信 |

**执行后端**（自动检测）：
- **进程内**：同一 Node.js 进程中的异步任务（最快）
- **tmux**：持久终端会话（断开连接后存活）
- **iTerm2**：可视分屏面板（仅 macOS）

**模式**：

```
并行专家模式：
负责人生成 3 个队友 → 每个审查不同方面（安全、性能、架构）
→ 队友并发工作 → 向负责人汇报 → 负责人综合

群体模式：
负责人创建共享任务队列 → 队友自组织并认领任务
→ 独立执行 → 向共享状态异步更新
```

**限制**：
- 5 分钟心跳超时后自动移除
- 队友活跃时无法清理团队
- 功能标记未正式记录（社区发现）
- 实验性功能无官方 Anthropic 支持

**何时使用**：
- 需要并行分析的大型代码库（4 个以上方面）
- 带独立子任务的长时间运行工作流
- 多个专门关注点的代码审查

**何时不使用**：
- 简单任务（开销不值得）
- 顺序依赖（标准子智能体足够）
- 生产关键工作流（实验性 = 不稳定）

- **社区**：[GitHub Issue #3013 - Parallel Agent Execution](https://github.com/anthropics/claude-code/issues/3013)
- **社区**：[mikekelly/claude-sneakpeek](https://github.com/mikekelly/claude-sneakpeek) - 启用功能标记的并行构建

### 智能体反模式：角色 vs 上下文控制

> **"子智能体不是用来拟人化角色的，而是用来控制上下文的"** - Dex Horty

**常见错误**：像组建人类团队一样创建智能体，带职位头衔。

❌ **错误**（拟人化）：
```
- 前端智能体（角色：UI 开发者）
- 后端智能体（角色：API 工程师）
- QA 智能体（角色：测试员）
- 安全智能体（角色：安全专家）
```

**为什么失败**：智能体不是有专业领域的人类。它们是用于计算效率的**上下文隔离工具**。

✅ **正确**（上下文控制）：
```
- 独立依赖分析智能体（范围：仅 package.json + 锁文件）
- 并行文件处理智能体（范围：批量编辑而不污染主上下文）
- 全新安全审计智能体（范围：安全重点分析，无先前假设）
- 独立模块测试智能体（范围：测试执行，不干扰主工作流）
```

**关键区别**：

| 拟人化（错误） | 上下文控制（正确） |
|----------------------------|-------------------------|
| "安全专家智能体" | "带隔离上下文的安全审计" |
| "前端开发者智能体" | "UI 组件分析（范围：仅 src/components/）" |
| "代码审查员智能体" | "不污染主上下文的 PR 审查" |
| 模仿人类团队结构 | 优化计算资源 |
| 基于职位角色 | 基于范围/上下文边界 |

**何时使用智能体**（好的理由）：
- **隔离上下文**：防止污染主对话上下文
- **并行处理**：可并发运行的独立操作
- **范围限制**：将分析限制在特定文件/目录
- **新鲜视角**：在无先前推理包袱的情况下分析
- **资源优化**：将重型操作卸载到单独的上下文窗口

**何时不使用智能体**（坏的理由）：
- ❌ 创建带职位头衔的假团队
- ❌ 扮演不同的"专业"角色
- ❌ 模仿人类组织结构
- ❌ 按学科分工（前端/后端/QA）而非按上下文边界

### 范围聚焦智能体

除了通用子智能体，**范围聚焦编排**为不同智能体分配不同的**上下文边界**，实现多视角分析。

**模式**：不是让一个智能体审查所有内容，而是生成**范围隔离**的智能体，每个用全新上下文分析不同方面：

```markdown
用户：使用范围聚焦分析审查新的支付服务：

智能体 1（安全范围）：分析认证、输入验证、
  注入向量、密钥处理、PCI DSS 合规。
  上下文：src/payment/、src/auth/、config/security.yml

智能体 2（性能范围）：分析数据库查询、N+1 问题、
  缓存机会、响应时间瓶颈。
  上下文：src/payment/repository/、src/database/、慢查询日志

智能体 3（API 设计范围）：分析错误消息、响应格式
  一致性、API 可发现性、文档完整性。
  上下文：src/payment/api/、docs/api/、tests/integration/

将所有三个范围分析综合到统一的审查中，
包含优先级排序的行动项。
```

**使用自定义智能体实现**：

```yaml
# .claude/agents/security-audit.md
---
name: security-audit
model: opus
tools: Read, Grep, Glob
---
用隔离上下文分析代码的安全问题：
- OWASP Top 10 漏洞
- 认证/授权缺陷
- 输入验证缺口
- 密钥暴露风险

范围：仅安全重点分析。报告发现的严重等级
（严重/高/中/低），不考虑性能或 UX 权衡。
```

```yaml
# .claude/agents/perf-audit.md
---
name: perf-audit
model: sonnet
tools: Read, Grep, Glob, Bash
---
用隔离上下文分析代码的性能瓶颈：
- 数据库查询效率（N+1、缺少索引）
- 内存泄漏和资源管理
- 缓存机会
- 算法复杂度问题

范围：仅性能重点分析。报告发现的预估
影响（高/中/低），不考虑安全或可维护性权衡。
```

**何时使用范围聚焦智能体：**
- 需要 3 个以上不同上下文边界的分析（安全范围、性能范围、API 范围）
- 相互竞争的关注点受益于隔离评估（性能 vs 安全 vs 开发者体验）
- 完整上下文会污染特定方面分析的大型代码库

**何时不使用范围聚焦智能体：**
- 简单审查（一个带完整上下文的智能体涵盖所有方面）
- 时间受限的情况（综合开销超过收益）
- 范围不真正独立的任务（需要重叠上下文）

### 理念

> "用更少做更多。智能的架构选择、更好的训练效率和聚焦的问题解决，可以与原始规模竞争。"
> — Daniela Amodei，Anthropic CEO

Claude Code 信任模型的推理能力，而非构建复杂编排系统。这意味着：
- 更少的组件 = 更少的失败模式
- 模型驱动的决策 = 更好的泛化
- 简单循环 = 易于调试
